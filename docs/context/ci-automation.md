| **Provision Tenant** (`provision-tenant.yml`)       | manual `workflow_dispatch` only                         | Provisions one tenant end to end for a `tenants` row already inserted by the admin app's "Add tenant" wizard Server Action (via the GitHub API): creates its Sanity project/dataset/CORS entry, seeds a fixed starter content template, creates and deploys its own Studio Vercel project to `studio-<slug>.<PLATFORM_DOMAIN>`, mints and persists its read-only Sanity token, maps its custom domain onto the _shared_ `apps/web` Vercel project, and creates a Sanity webhook on its project pointing at that same shared `apps/web` app's `/api/revalidate` endpoint (signed with `SANITY_REVALIDATE_SECRET`) so publishing content there triggers cache revalidation. Runs in the `production` GitHub Environment (same credentials store every other prod-affecting job uses). Every step is independently idempotent — re-dispatching the same `tenantId` resumes at the first incomplete step rather than repeating finished work — and reports each step's status back to `apps/admin`'s `/api/provisioning/status-callback` route, both on success and failure. Logic lives in `packages/db/scripts/provision-tenant/` (a `tsx --conditions=react-server` Node script, same execution pattern as `scripts/seed-tenant.ts`), not in the workflow YAML itself. Deliberately manually-triggered only, same posture as Refresh Dev Dataset — it fails loudly rather than no-op-green when a required secret is missing. Accepts an optional `adminAppBaseUrl` input that overrides `ADMIN_APP_BASE_URL` for that one dispatch (e.g. a local tunnel URL for manual testing); left blank, it falls back to the `production` Environment's value — the real dispatch from `apps/admin` never sets this input, so it's unaffected. |
| **Deprovision Tenant** (`deprovision-tenant.yml`)   | manual `workflow_dispatch` only                         | Reverses Provision Tenant for one tenant: removes its custom domain from the shared `apps/web` Vercel project, deletes its Studio Vercel project, deletes its Sanity project (its dataset/CORS entries/robot tokens/webhooks go with it), clears the persisted Sanity credentials and other provisioning-artifact columns on the `tenants` row, then archives the row by stamping `deprovisionedAt` — never a hard delete, so the slug's unique constraint keeps it from being silently re-registered. Destructive, so two safety gates apply before any deletion: a `confirm` input that must match the tenant's live slug exactly, and a `dryRun` input defaulting to `true` (an operator must explicitly set it to `false` to delete anything). Runs in the `production` GitHub Environment, same as Provision Tenant. Every step is independently idempotent (404-tolerant deletes, column-presence checks) — a retry after a partial failure resumes safely. Logic lives in `packages/db/scripts/deprovision-tenant/`, same execution pattern as `provision-tenant/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

**Required status checks on `main`:** Type-check, Lint, Test, Typegen, Build,
Migrations, Dependency Review, Zizmor, Actionlint, Knip, Commitlint, and
Hooks (`Shellcheck + guard tests`). Everything else (Claude Code, Document
validation, Lighthouse CI, Playwright smoke) stays advisory: a red result
there does not currently block a merge.
Required workflows run on every PR without path filters on purpose — a
path-skipped workflow leaves its required checks pending forever (see the
comment in `ci.yml`). Document validation is a separate job inside `ci.yml`
from the required Migrations job precisely so a routine drift in an existing
live document (independent of any given PR's diff) can't fail a required
check — same reasoning as Lighthouse CI / Playwright smoke below.

**Document validation always warns once, on `migrationState`, by accepted
design.** `migrationState` (`apps/cms/scripts/migrate.mjs`'s single fixed-`_id`
migration ledger document) is deliberately not a Studio schema type — it's
tooling infrastructure, never edited via the Studio UI. `sanity documents
validate` has no exclusion flag for a `_type`/`_id` (checked against the CLI's
own `--help` and source as of `sanity@^6.8.0`/CLI `7.15.1` — none exists), so
it always emits `Could not find schema type for type 'migrationState',
skipping validation`. Harmless and expected — the job is advisory, so this
carries no functional cost. Don't chase it with a schema entry; that would
add Studio-schema surface for a document nothing but `migrate.mjs` ever
touches.

**Lighthouse CI and Playwright smoke stay advisory by design, and both run
only on push to `main`, not on every PR push.** Playwright smoke is still a
structural no-op — it depends on a preview/smoke URL this repo doesn't
produce yet (no PR preview deploys, per `SPEC.md` §13) — so promoting it
stays a deliberate follow-up once `SMOKE_URL` is configured and it can
genuinely fail. Lighthouse CI targets production and **can** genuinely fail
— it stays advisory anyway because it checks production's current health
rather than the merge's own diff (no per-PR preview target exists or is
currently tracked), which makes a blocking failure there potentially
unrelated to the change that triggered it. Both were moved off
every-PR-push to merge-to-main-only: neither ever gated on the PR's own
diff (same production/live-URL target regardless of which PR pushed), so a
PR-push trigger only paid the run cost without adding signal a post-merge
run doesn't already give.

**`apps/web`'s Storybook coverage is a hosted Vercel deployment, not a CI
workflow** — mirroring `packages/ui`'s existing `blog-storybook` project
(neither appears in the table above; a hosted Vercel deployment isn't a
GitHub Actions workflow). A second Vercel project, rooted at the repo root
(`vercel.json`, scoped via turbo to `storybook:build --filter=web`), builds
and previews `apps/web`'s own stories on every PR — see
[`docs/DEPLOY.md`](../DEPLOY.md)'s Storybook section for the setup.

One-time environment setup (datasets, tokens, Vercel projects, secrets,
webhooks, CORS) is human-gated console work — see [`docs/DEPLOY.md`](../DEPLOY.md)
and `SPEC.md` §13. Manual `sanity deploy` / Vercel deploys are never run by
hand (agent permissions deny them; the pipeline owns deploys).
