| **Provision Tenant** (`provision-tenant.yml`)           | manual `workflow_dispatch` only                                        | Provisions one tenant end to end for a `tenants` row already inserted by the admin app's "Add tenant" wizard Server Action (via the GitHub API): if the row is a previously-deprovisioned tenant being re-provisioned, first un-archives its existing Sanity project (`isDisabledByUser: false`) so the reactivated tenant's content API works again — then creates its Sanity project/dataset/CORS entry, seeds a fixed starter content template, mints and persists its read-only Sanity token, maps its custom domain onto the _shared_ `apps/web` Vercel project, and creates a Sanity webhook on its project pointing at that same shared `apps/web` app's `/api/revalidate` endpoint (signed with `SANITY_REVALIDATE_SECRET`) so publishing content there triggers cache revalidation. Runs in the GitHub Environment named by the required `environment` input (`development`/`production`, default `production`) — every credential the job needs, including the tenant registry connection string (`secrets.TENANT_REGISTRY_DATABASE_URL`, kept separate from `DATABASE_URL_UNPOOLED`, which `deploy-production.yml`'s `migrate-db` job reads instead), resolves from that same Environment, so a dispatch never mixes one environment's tenant registry with another's Sanity/Vercel credentials. Every step is independently idempotent — re-dispatching the same `tenantId` resumes at the first incomplete step rather than repeating finished work — and writes each step's status directly to Postgres (via `@blog/db`'s `updateProvisioningStep`, no HTTP hop to `apps/platform`), both on success and failure. Each of those writes also stamps that step's `updatedAt`, and the run as a whole records a `run` object (`startedAt`/`finishedAt`/`registry`/`workflowRunUrl`) alongside the step keys in the same `provisioning_steps` jsonb payload — `registry` being the dispatched `environment` input, passed in as `TENANT_REGISTRY_ENVIRONMENT`, and the workflow-run URL built from Actions' own default `GITHUB_SERVER_URL`/`GITHUB_REPOSITORY`/`GITHUB_RUN_ID` (which need no `env:` entry). `apps/platform`'s provisioning page renders both, so a failed run's timeline is readable without opening this workflow's log. Logic lives in `packages/db/scripts/provision-tenant/` (a `tsx --conditions=react-server` Node script, same execution pattern as `scripts/seed-tenant.ts`), not in the workflow YAML itself. Deliberately manually-triggered only, same posture as Refresh Dev Dataset — it fails loudly rather than no-op-green when a required secret is missing. Accepts optional `adminAppBaseUrl` and `tenantSanityDataset` inputs that override `ADMIN_APP_BASE_URL`/`TENANT_SANITY_DATASET` for that one dispatch (e.g. a local tunnel URL, or `development`, for manual testing); left blank, each falls back to the dispatched environment's own value — the real dispatch from `apps/platform` never sets either input, so it's unaffected. Once core provisioning finishes, also runs the same post-provisioning owner-elevation check Recheck Tenant Owners' sweep runs (`elevateTenantOwner`) and, via the shared `notifyOwnerElevationOutcome` helper (`packages/db/scripts/provision-tenant/lib/notify-owner-elevation-outcome.ts`), emails every `ADMIN_ROLE.SUPERADMIN` admin through the optional `RESEND_API_KEY` job env var if the outcome is notifiable (`STALLED`/`AMBIGUOUS_MEMBERSHIP`) — see the Recheck Tenant Owners row below for the shared de-dup mechanism. |
| **Deprovision Tenant** (`deprovision-tenant.yml`)       | manual `workflow_dispatch` only                                        | Reverses Provision Tenant for one tenant: removes its custom domain from the shared `apps/web` Vercel project, archives its Sanity project by setting `isDisabledByUser` — which stops its subscription and blocks API/CDN access, and unlike deleting a project does not require an org billing permission this token deliberately lacks, so the project and its dataset survive for a later permanent tenant delete — clears the persisted Sanity credentials and other provisioning-artifact columns on the `tenants` row, then archives the row by stamping `deprovisionedAt` — never a hard delete, so the slug's unique constraint keeps it from being silently re-registered. Finally it POSTs the archived tenant's id to `apps/web`'s `/api/revalidate-site-config`, purging that tenant's cache tags so the archived site stops being served from the prerender cache instead of waiting out its fallback window; this step needs `vars.WEB_APP_URL` and `secrets.SITE_CONFIG_REVALIDATE_SECRET` from the same Environment, and — unlike every other credential the job reads — they are deliberately **not** validated up front, so a missing value can never block the destructive teardown steps that precede it. It is also the one step that is **not** idempotent-on-retry: the run-level `deprovisionedAt` guard short-circuits an already-archived tenant, so a re-run dispatched specifically to retry a failed invalidation returns "already deprovisioned" without reaching it, and the purge must instead be driven by hand against the endpoint. Destructive, so two safety gates apply before any deletion: a `confirm` input that must match the tenant's live slug exactly, and a `dryRun` input defaulting to `true` (an operator must explicitly set it to `false` to delete anything). Runs in the GitHub Environment named by the required `environment` input, same as Provision Tenant — every credential the job needs, including the tenant registry connection string (`secrets.TENANT_REGISTRY_DATABASE_URL`), resolves from that same Environment (see the Provision Tenant row above). Every step is independently idempotent (404-tolerant deletes, column-presence checks) — a retry after a partial failure resumes safely. Archiving also records one `ARCHIVED`/`TENANT` row in `audit_events`, attributed to the dispatching GitHub user (`actor_id` `github:<login>`) from the `GITHUB_ACTOR`/`GITHUB_RUN_ID` defaults Actions sets on every step — a dry run or an already-archived tenant records nothing, and a failed audit write is logged and swallowed rather than failing the step whose destructive work already succeeded. Logic lives in `packages/db/scripts/deprovision-tenant/`, same execution pattern as `provision-tenant/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Recheck Tenant Owners** (`recheck-tenant-owners.yml`) | `schedule:` every 6 hours (`0 */6 * * *`) + manual `workflow_dispatch` | Sweeps every fully core-provisioned, active tenant (`status = ACTIVE`, `provisioningStatus = READY`) and re-checks its Sanity project ACL, promoting the owner from `viewer` to `administrator` once they've accepted their invite (`elevateTenantOwner`, the same function Provision Tenant's own single post-provisioning check calls). Provision Tenant only checks once, right after core provisioning; a human owner routinely accepts well after that single check, so this scheduled sweep is the recurring re-check needed to detect a stalled acceptance without waiting on an unrelated deploy. The 6-hour cadence gives ~12 checks within `elevateTenantOwner`'s existing 3-day stall threshold (`OWNER_ACCEPTANCE_STALL_THRESHOLD_MS`) — good resolution for surfacing a stall promptly, while also elevating a genuinely-accepted owner within hours rather than up to a day later. One candidate's failure never aborts the sweep for the rest (per-tenant try/catch), and re-checking a settled (already-`administrator`) owner is a cheap no-op single ACL read — repeated checks stay cheap even for a tenant that never accepts. Needs only `SANITY_MANAGEMENT_TOKEN` and the tenant registry connection string — no Vercel credentials, this workflow never touches Vercel. Like Provision Tenant/Deprovision Tenant, its job binds its GitHub Environment to its own optional `environment` input (`development`/`production`, default `production`), so the registry connection string and every other credential resolve from the Environment that dispatch names rather than a fixed one. Unlike those two it also runs on a `schedule:`, and a scheduled run carries no `inputs` context at all, so it binds that input with a `'production'` fallback: every cron sweep targets `production`, and only a manual dispatch reaches `development`. Logic lives in `packages/db/scripts/recheck-tenant-owners/`, same execution pattern as `provision-tenant/`/`deprovision-tenant/`. Each check's outcome is persisted to the tenant's `OWNER_ELEVATION` provisioning step (`reportOwnerElevationOutcome`), so the platform admin panel can render it. The job's `RESEND_API_KEY` (optional — same shared secret name `apps/web`/`apps/platform` already use) emails every `ADMIN_ROLE.SUPERADMIN` admin, via the shared `notifyOwnerElevationOutcome` helper (`packages/db/scripts/provision-tenant/lib/notify-owner-elevation-outcome.ts`), when a tenant's outcome is `STALLED`/`AMBIGUOUS_MEMBERSHIP`. De-duplication keys on the `tenants.lastNotifiedOwnerElevationOutcome` column — the outcome last actually communicated, written by this same helper right after a successful send — rather than the most recently _observed_ outcome, so a same-day sweep never re-sends for an outcome unchanged since the last notification, whether that notification happened on an earlier sweep or during Provision Tenant's own post-provisioning check (see that row above). Unset `RESEND_API_KEY` skips only the notification, never the sweep itself (`notifyOperatorsOfOwnerElevationOutcome`).                                                                                                                                                                                                                                                                                                                                                                                                      |

**Required status checks on `main`:** Type-check, Lint, Test, Typegen, Build,
Migrations, Dependency Review, Zizmor, Actionlint, Knip, Commitlint, and
Hooks (`Shellcheck + guard tests`). Everything else (Claude Code, Document
validation, Lighthouse CI, Playwright smoke) stays advisory: a red result
there does not currently block a merge.
Required workflows run on every PR without path filters on purpose — a
path-skipped workflow leaves its required checks pending forever (see the
comment in `ci.yml`). Document validation is a separate job inside `ci.yml`
from the required Migrations job precisely so a routine drift in an existing
live document (independent of any given PR's diff) can't fail a required
check — same reasoning as Lighthouse CI / Playwright smoke below.

**Document validation runs clean, including on `migrationState`.**
`migrationState` (`packages/studio/scripts/migrate.mjs`'s single fixed-`_id`
migration ledger document) has a declared Studio schema type
(`packages/studio/src/schema-types/documents/system/migration-state.ts`) so
`sanity documents validate` recognizes it, while `sanity.config.ts` disables
every Studio document action and excludes it from the new-document menu —
it's still never edited via the Studio UI. This supersedes an earlier
decision (#1580) to leave it unrecognized as an accepted warning; #1882
revisited that call and declared the type instead, since the job being
advisory doesn't make an avoidable warning worth carrying indefinitely.

**Lighthouse CI and Playwright smoke stay advisory by design, and both run
only on push to `main`, not on every PR push.** Playwright smoke is still a
structural no-op — it depends on a preview/smoke URL this repo doesn't
produce yet (no PR preview deploys, per `SPEC.md` §13) — so promoting it
stays a deliberate follow-up once `SMOKE_URL` is configured and it can
genuinely fail. Lighthouse CI targets production and **can** genuinely fail
— it stays advisory anyway because it checks production's current health
rather than the merge's own diff (no per-PR preview target exists or is
currently tracked), which makes a blocking failure there potentially
unrelated to the change that triggered it. Both were moved off
every-PR-push to merge-to-main-only: neither ever gated on the PR's own
diff (same production/live-URL target regardless of which PR pushed), so a
PR-push trigger only paid the run cost without adding signal a post-merge
run doesn't already give.

**`apps/web`'s Storybook coverage is a hosted Vercel deployment, not a CI
workflow** — mirroring `packages/ui`'s existing `ui-library` project
(neither appears in the table above; a hosted Vercel deployment isn't a
GitHub Actions workflow). A second Vercel project, rooted at the repo root
(`vercel.json`, scoped via turbo to `storybook:build --filter=web`), builds
and previews `apps/web`'s own stories — see
[`docs/DEPLOY.md`](../DEPLOY.md)'s Storybook section for the setup.

Both Storybook projects share one `ignoreCommand` script,
`scripts/vercel-ignore-affected.sh`, in **two modes**.

`ui-library` uses **affected mode**
(`vercel-ignore-affected.sh <package> <watched-paths…>`): a push builds it
only when turbo sees `@blog/ui` as **affected**, _or_ when one of its watched
deploy-config paths changed — its own `vercel.json` and the shared ignore
script itself. Watching the config files means a deploy-config change (which
turbo can't see as "affecting" the package) still gets validated by a real
build instead of being silently skipped; watching the script means a change
to the skip logic self-verifies.

`web-ui-library` uses **allowlist mode**
(`vercel-ignore-affected.sh --paths <trigger-paths…>`), which drops turbo and
builds only when one of the named paths changed: the two deploy-config paths
above, plus `apps/web/.storybook`, `apps/web/**/*.stories.tsx`, `packages/ui`
and `configs/tailwind`. Affected mode was a poor fit here because the project
is scoped to the `web` package, which nearly every commit touches — it
rebuilt on ~41% of all pushes (252 of 609 over twelve days) while the stories
themselves had not moved, and Storybook builds were the single largest
consumer of the account's Vercel build-CPU allowance. Naming the real inputs
confines rebuilds to commits that can actually change the output. The trade
is a deployed Storybook that lags a plain component edit until a story,
`@blog/ui`, or the Tailwind preset moves — acceptable for a browsable
reference that is run locally (`pnpm storybook`) during development. Note
that a dependency bump alone (`pnpm-lock.yaml`) is deliberately **not** a
trigger; bump Storybook or Vite and the deployed build stays stale until one
of the listed paths moves.

Everything outside a project's triggers skips, so an unrelated PR builds
neither Storybook.

**Which commit the diff is taken against** decides all of the above, and it
depends on the situation:

- `VERCEL_GIT_PREVIOUS_SHA` when Vercel supplies one — the last **successful**
  deployment for that project and branch.
- Otherwise the merge-base with `main`, fetched by explicit URL (Vercel's build
  clone has no `origin` remote).
- Otherwise `HEAD^1`. This last step is what makes a **`main` build** work: on
  `main`, `FETCH_HEAD` is `main`, so the merge-base resolves to `HEAD` itself,
  and a commit diffed against itself shows nothing affected. Before this rule
  existed, a project that had never deployed successfully skipped every single
  `main` build — which never produced a deployment, so `VERCEL_GIT_PREVIOUS_SHA`
  stayed empty and the next merge repeated it. `web-ui-library` sat in exactly that
  deadlock, showing "No Production Deployment", until it was broken.

In **affected mode**, a change touching **only**
`packages/config/src/types/**` or `packages/config/src/sanity/generated/**`
skips regardless of affectedness. Turbo marks every dependent affected by any
`packages/config` change, but both `storybook:build` scripts are a bare
`storybook build`, which transpiles without type-checking — so type-only files
can neither reach the output nor break the build. A type-only file alongside
any other change still builds. Allowlist mode needs no such carve-out:
`packages/config` is not a trigger path, so it skips by construction.

`scripts/vercel-ignore-affected.test.sh` pins all of this (see the Hooks row
above); the script has no failing signal of its own, so a regression here is
invisible until someone notices a project has stopped deploying.

One-time environment setup (datasets, tokens, Vercel projects, secrets,
webhooks, CORS) is human-gated console work — see [`docs/DEPLOY.md`](../DEPLOY.md)
and `SPEC.md` §13. Manual `sanity deploy` / Vercel deploys are never run by
hand (agent permissions deny them; the pipeline owns deploys).
