# Newsletter

## What it does

An editor places a Newsletter Signup module on a page; a reader enters an email address, gets a confirmation email and becomes an active subscriber by clicking its link (double opt-in). The confirmation email carries a one-click unsubscribe link, and a signed-in reader can unsubscribe or resend the confirmation from `/account`. A post's first publish emails it to the site's confirmed subscribers through the worker's send run (below). An owner turns the Newsletter capability on and off on the platform's Features page; it is `GROWTH` only, so on `FREE` and `STARTER` its switch is locked unless a grant opens it.

## Surfaces and routes

- **Studio** — each post's "Send to subscribers" switch (`sendToSubscribers`), beside Published At: on for a new post, off on every starter post. It marks the post to be emailed once, on its first publish, and never on a later edit; the worker's send run reads it. Its description names the confirmed count ("your confirmed subscribers" at 0 or when the status can't be read). The field reads the platform's status route (below) when the post opens, shows a spinner until it answers, and re-reads after each publish:
  - **On a plan without Newsletter** (off cause `NOT_IN_PLAN`), and on a post whose claim was skipped `NOT_IN_PLAN`, the field is hidden — switch, status and Send emails — so a post published before an upgrade never shows it.
  - **With no claim** (never published, or a claim the worker released) the switch shows, disabled with its cause's note while the site is not active, Newsletter is off in Features or the sending setting is off.
  - **Once a claim exists** a read-only status replaces the switch: Emailed (count and date), Sending (how many reached so far, once the run has counted its recipients), a neutral "checking" line for a claim the run has not counted yet (it may still be scheduled or skipped), Scheduled (the publish date), or Not emailed. Both in-flight states are re-read every 10 s until they settle; a failed read keeps the last status and keeps re-reading. A band or month skip says why, that it can be sent with Send emails, and links to Subscribers; each with no link, an operator pause reads "Sending is paused for this site.", a reputation stop says sending was paused because too many emails bounced or were marked as spam, and a suspended site says it is suspended (as does the disabled switch while it stays suspended); a post published while Newsletter or the sending setting was off says so, with a link to Features or Subscribers only while that cause still holds.
  - **Send emails** shows under the status, or under the switch on a published post with no claim, whenever the status route offers it — except for the first minute after a publish while the post still has no claim, when the field keeps re-reading so the publish webhook can take it. It is disabled, with the first reason that applies, until the site is sending and the month's emails cover every confirmed subscriber. Pressing it opens a confirm dialog naming the recipients and the emails it uses (focus on Cancel; Escape closes); confirming calls the send-now route, toasts "Sending to {n} subscribers." or "This post can't be sent right now.", and re-reads the status.
- **Studio** — "Send me a test", the first item of a post's actions menu ("Emails this post to you only"): it reads the post as last saved (the draft, else the published version) and posts its fields to the platform's test-send route, which emails it to the signed-in user alone through the platform account. Toasts confirm the address the platform sent it to (the platform session's, which can differ from the Studio login), say to try again in a minute, or name the time the test limit (5 an hour, 20 a day per person, shared with the Email page's test) lets them try again.
- **Platform, Studio routes** — `GET /api/studio/newsletter-post/status`, `POST /api/studio/newsletter-post/test-send` and `POST /api/studio/newsletter-post/send-now`, each taking the Studio's Sanity project id to find the tenant and admitting its owner, editors and operators (`resolveStudioCaller`); the contract lives in `@shinefold/config` (`SPEC.md` §5).
- **Studio** — `module_newsletter` ("Newsletter Signup"): title, brand variant, variant (Full or Compact), heading block, copy, up to two trust cues, alignment, layout. Pickers relabel it "(off in Features)" and its documents warn while the capability is off.
- **Public site** — the module on any page with a module list. Full shows copy and trust cues in a panel; Compact drops the supporting text, copy and trust cues.
- `GET /api/newsletter/confirm?token=&lang=` — confirms, then redirects (303) to the result page.
- `GET /api/newsletter/unsubscribe?token=&lang=` keeps the token in a cookie and redirects (303) to the confirmation page, or to the invalid-link result page when the token is missing; `POST` to the same path deletes the subscription, taking the token from the query string (the `List-Unsubscribe-Post` one-click target) or else from that cookie, then clears the cookie and redirects (303) to the result page.
- `/[locale]/newsletter/unsubscribe` — the confirm button, in the site's layout, theme and the link's language; it `POST`s to the unsubscribe path with no token in either URL, so the token never reaches analytics, history or a `Referer`. ISR like the result pages, `noindex`.
- `/[locale]/newsletter/[result]` — the confirm or unsubscribe outcome (`NEWSLETTER_RESULT`: confirmed, unsubscribed, or an invalid, failed or unavailable link) in the site's layout, theme and the link's language, with a link home; `noindex`.
- `/[locale]/account` — the Newsletter section (see [reader-account](./reader-account.md)).
- **Platform** — the Features toggle, the Email page's `NEWSLETTER_CONFIRMATION` template, and the Subscribers page below.
- **Platform, `/dashboard/subscribers` and `/tenants/[tenantId]/subscribers`** — for a site whose plan (with grants) includes Newsletter. Subscriber lists are sensitive, so one rule (`canManageSubscribers`) decides the dashboard page, its sidebar entry, the Overview's usage link and the page's actions: the site's owner passes, and an operator passes only on a site they really own or, as a super admin, on a live site created from the platform (`createdFromPlatform`, `canOperatorOpenSubscribers`). The operator tenant view, where the entry sits beside Leads, shows it only on that last condition. An admin sees no entry in any tenant view; a self-serve site the super admin does not own, and an archived site, have none for operators; the route is not found for each. An editor, and a Free or Starter site, get neither page nor entry. Each route keeps its links on itself: it pages its own list, and the empty state opens that site's Studio. It shows:
  - the confirmed count and Export CSV (`exportSubscribersAction`: every confirmed subscriber as `email,confirmed_at`, UTC ISO times, newest first, named `subscribers-{first label of the platform address, else the main address}-{UTC day}.csv`; disabled with no subscribers);
  - at most one notice, in this order: the operator pause (`newsletter_paused_at` set, or the reputation at `STOP`), over the band, out of this month's emails, near the band, near the emails (80%), then "After moving up" when the `MOVED_UP` search param names the band the site is now on. A paused notice names the newest post skipped for its reason since the last sent post (`getLatestSkippedNewsletterPost`), or drops that sentence. The move-up button (`MoveUpBand`) shows for the owner only, and only with a catalogue price for the site's stored interval and currency; on the 25,000 band the note reads "You're on the largest band.";
  - the subscriber-band and emails-this-month cards, each a meter with a note that is muted below 80%, warning from 80% and error-toned only while its own paused notice shows ("paused" uses the worker gate's rules: over the band is more subscribers than the ceiling, out of emails is more subscribers than the emails left);
  - the "Email new posts to subscribers" switch (`setEmailNewPostsAction`, saved on change, reverted with an error on failure) and the paged list, 25 a page newest first, each row with a confirm-first remove (`removeSubscriberAction`, `unsubscribeById`). Below `md` the list is a `<ul>` whose footer hides Previous on page 1.
  - With no subscribers: no switch and no list, but a card linking to the site's Studio page list.
- **Platform, Overview** — the Usage card's emails row links to the Subscribers page and, while the next post would not fit this month, reads "Sending paused".
- **Platform, operator** — a paused site's tenant overview (`/tenants/[tenantId]`) shows every admin a "Newsletter paused" card with the date it was paused; an unpaused site shows none. Only a super admin gets its "Clear pause" confirm, which calls `clearNewsletterPauseAction` (`apps/platform/src/server/newsletter-pause/`, behind `requireSuperAdmin`). The clear write decides: when it clears nothing the action refuses `NOT_PAUSED` and a toast says the pause was already cleared; otherwise it records `NEWSLETTER_PAUSE_CLEARED` against the tenant with the cleared `pausedAt`. Either way the dialog closes, focus moves to the page heading and the page refreshes.

## Data

- Sanity: `page_post.sendToSubscribers` (boolean, optional; initial value `true`). `module_newsletter` documents; trust cues are `newsletterTrustCue` objects (localized `text`, max 40 characters). Loaded through `service.modules.newsletter.v1.getNewsletter`, ISR-tagged `modules:newsletter` and `module:<id>`.
- Neon `subscribers`: `id`, `tenant_id` (cascade), `email` (normalized), `status` `SUBSCRIBER_STATUS` (`PENDING` | `ACTIVE`, from `@shinefold/db/constants`), `confirmation_token_hash` (unique SHA-256 hex of the emailed confirm token; the raw token is never stored), `subscribed_at`, `confirmed_at`, `confirmation_sent_at` (the last confirmation send, claimed atomically). The address is stored only encrypted (`email_encrypted`, `PERSONAL_DATA_ENCRYPTION_KEY`), with two keyed HMACs under `PERSONAL_DATA_INDEX_KEY`: `email_index` ignores case and any `+tag`, and `email_exact_index` keeps the `+tag`. Unique (`tenant_id`, `email_exact_index`), so `a+x@d` and `a@d` stay separate subscriptions; a row written before that column existed has none and is not covered by the rule. Every read uses those: a signup finds its row through the index, then keeps only the row whose decrypted address equals the submitted one ignoring case, and emails that address; and the account section and `/account` actions find a reader's row through the index of their decrypted account email, then keep only the row whose decrypted address equals it ignoring case, so an account never reaches a `+tag` sibling's subscription; a resent confirmation goes to that row's address. No user FK: a signed-out reader can subscribe.
- Neon `newsletter_post_sends`: one row per (`tenant_id`, `post_id`) with `claimed_at`. `queries.newsletterPostSends.claimNewsletterPostSend(tenantId, postId)` inserts it and returns the claim, or `null` when the post was already claimed, so of two concurrent claims exactly one wins. `releaseNewsletterPostSend(tenantId, postId, claimedAt)` gives a claim back, deleting the row only while its `claimed_at` still equals the claim's, so a newer claim is never released, and never once an outcome is recorded. `post_id` is the Sanity document id as plain text. A claim records its outcome once: `markNewsletterPostSent` sets `outcome` to `SENT` and `markNewsletterPostSkipped(tenantId, postId, reason)` sets `SKIPPED` with a `skip_reason` (`NEWSLETTER_SKIP_REASON`, in `@shinefold/config` so the Studio can read it: the gate's `OVER_SUBSCRIBER_BAND`, `OVER_MONTHLY_ALLOWANCE`, `REPUTATION_STOP` and `SITE_PAUSED`, and the four off causes `NOT_IN_PLAN`, `SITE_INACTIVE`, `NEWSLETTER_OFF` and `SENDING_OFF`, which `NEWSLETTER_SENDING_OFF_CAUSES` lists in the order they are checked; `NEWSLETTER_HAND_SENDABLE_SKIP_REASONS` lists the skips Send emails may clear), each only while no outcome is recorded, returning whether it wrote one. A skipped claim stays, so the post is never sent later. `getNewsletterPostSend` reads the claim, its outcome and reason (`undefined` while the send is in flight). A post's first publish takes the claim (below), and the worker's send run records the outcome. The Studio-to-platform contract for a post's send status, its test send and Send emails — `NEWSLETTER_SEND_STATUS`, `TNewsletterPostSendStatusResponse`, `NEWSLETTER_SEND_STATUS_REFUSAL`, `NEWSLETTER_TEST_SEND_REFUSAL`, `NEWSLETTER_SEND_NOW_REFUSAL` (each route refuses a caller outside the site with its own `FORBIDDEN`; the test-send and Send emails `POST`s first refuse, with that same `FORBIDDEN` and before the caller is resolved, any request that is not `application/json` or whose `Origin` is not the platform's own — or, with no `Origin`, whose `Sec-Fetch-Site` is not `same-origin` — because tenant sites share the platform's registrable domain and its `SameSite=Lax` session cookie reaches their posts), their result types and the three route paths in `routes` — lives in `@shinefold/config` (`constants/newsletter-post-send.ts`), the one package both import.
- A claim also carries what the Studio and the Subscribers page show: `post_title` and `post_published_at`, `recipient_count` (how many subscribers the send targets), `sent_count` (how many it has reached, starting at 0), `scheduled_for` (the date a scheduled post waits for), `settled_at` (set by `markNewsletterPostSent`, `markNewsletterPostSkipped` and `markNewsletterPostFailed`), `emails_needed`, `allowance_left` and `band_ceiling` (the band the skip was measured against; on a limit skip only) and `hand_started_at`. `markNewsletterPostSkipped` takes those skip details, and the post's title and date, as an optional fourth argument, so a post skipped before its send starts keeps them. The run's writes each touch only the claim it holds (same `claimed_at`, no outcome) and return whether they wrote: `setNewsletterPostSendSchedule(tenantId, postId, claimedAt, scheduledFor)`, `recordNewsletterPostSendStart(tenantId, postId, claimedAt, { postTitle, postPublishedAt, recipientCount })` and `setNewsletterPostSendProgress(tenantId, postId, claimedAt, sentCount)`, which sets `sent_count` to the run's running total, so a replayed page step writes the same value. `markNewsletterPostSent` also sets `recipient_count` to `sent_count`, so a list that changed mid-send still ends with the two equal. `markNewsletterPostFailed` settles a claim with outcome `FAILED`, keeping `sent_count` and `recipient_count` as they stood, for a run that cannot finish. `getNewsletterPostSend` returns every column.
- `startNewsletterPostSendByHand(tenantId, postId)` is Send emails' one statement: it claims a post with no claim, or clears a `SKIPPED` claim whose reason is in `NEWSLETTER_HAND_SENDABLE_SKIP_REASONS` (its outcome, skip fields, schedule, recipient and sent counts and `settled_at`; the title and date stay), setting `hand_started_at` and a new `claimed_at`. It returns the new `claimedAt` with the skip reason, emails needed, allowance left and band ceiling it cleared, so a failed enqueue can put the skip back (or release a fresh claim), and `undefined` when it refuses: a post skipped for `NOT_IN_PLAN`, `SITE_INACTIVE`, `SITE_PAUSED` or `REPUTATION_STOP`, or a claim that is queued, scheduled, sending or sent, so of two presses only one starts a run.
- `getLatestSkippedNewsletterPost(tenantId, reason)` returns the post a paused notice names: the newest claim skipped for that reason whose `settled_at` is after the site's last sent post, with its title, date, emails needed, allowance left and `skippedAt`, or `undefined`. Its reason excludes the four off causes by type.
- `getNewsletterSendingOffCause(tenantId)` is the one answer to why a site is not sending posts, for web, the worker and the platform: it reads the tenant (`DB_NOT_FOUND` when there is none), resolves its plan with its open grants (`listResolvableEntitlementGrants`, `resolveTenantEntitlements`, so a grant counts), reads the Features row (a site without one reads its preset's Newsletter default from `PRESET_REGISTRY`, `CONSOLE` when the preset is unset, as web and the Features page do) and `email_new_posts`, and returns the first of `NEWSLETTER_SENDING_OFF_CAUSES` that applies, or `undefined` when the site sends posts. The decision itself is `newsletterSendingOffCause(tenant, { capabilities, newsletterEnabled, emailNewPosts })` (`@shinefold/db/utils/newsletter-sending-off-cause`), where active is `isTenantWritable` (a writable status and not deprovisioned). The operator pause and the band stay the gate's.
- Neon `newsletter_limit_notices`: one row per (`tenant_id`, `month`, `kind`) with `sent_at`, `month` being the UTC month's first day. `markNewsletterLimitNoticeSent(tenantId, kind)` inserts it and returns whether it did, so of two runs only one sends the email, and each month starts fresh. `releaseNewsletterLimitNotice(tenantId, kind)` deletes this month's row, so a notice whose send failed can be sent again. `NEWSLETTER_LIMIT_NOTICE_KIND`: `SUBSCRIBER_BAND_NEAR` and `MONTHLY_ALLOWANCE_NEAR` (80% of the limit), `SENDING_PAUSED`.
- Pause: `email_config.newsletter_paused_at`, null when not paused. `pauseNewsletter(tenantId)` sets it (keeping an earlier pause's time, creating the row if missing) and returns it; `clearNewsletterPause` sets it back to null only while it is set and returns the time it cleared (`undefined` when nothing was paused, so of two concurrent clears only one gets a time); `getNewsletterPausedAt` reads it (`undefined` when not paused).
- Reputation gate: `emailReputationLevel(reputation)` (`@shinefold/db/utils/email-reputation-level`) maps `getEmailReputation`'s result to `EMAIL_REPUTATION_LEVEL` `OK`, `WARN`, `SLOW` or `STOP` — the most severe level either rate reaches, at or above its threshold in `EMAIL_REPUTATION_THRESHOLDS` (bounces 2% / 2.5% / 3%, complaints 0.03% / 0.05% / 0.06%, below Resend's own pause levels). Below 20 resolved emails (`EMAIL_REPUTATION_MIN_RESOLVED_COUNT`) it is always `OK`.
- For sending, `listActiveSubscribers(tenantId, pageSize, afterId)` pages through a tenant's `ACTIVE` subscribers in `id` order with their decrypted addresses (keyset: pass the last id of the previous page; index `subscribers_tenant_status_id_idx` on (`tenant_id`, `status`, `id`)). An address the configured keyring cannot decrypt comes back as `undefined`, so one bad row never fails the page, and the caller counts the addresses it skips; an unset or malformed `PERSONAL_DATA_ENCRYPTION_KEY` still throws, and `countActiveSubscribers(tenantId)` counts them; `countSubscribersForTenant` still counts every status. `unsubscribeById(tenantId, subscriberId)` removes one subscriber.
- For the Subscribers page, `listSubscribersPage(tenantId, { page, pageSize })` returns `{ rows: { id, email, confirmedAt }[], total }` — confirmed subscribers only (`ACTIVE` with a `confirmed_at`), newest confirmed first, `page` counted from 1 — and `listSubscribersForExport(tenantId)` returns every confirmed subscriber's `email` and `confirmedAt`, newest first, read 1,000 at a time by keyset on (`confirmed_at`, `id`); both use the index `subscribers_tenant_status_confirmed_at_id_idx`. An address that will not decrypt is `undefined` in both, as in `listActiveSubscribers`.
- Test sends are limited by a stored count, not in memory: `test_email_send_counters` has the shape of `magic_link_send_counters` (`key`, `window_started_at`, `count`), and `incrementTestEmailSendCount(key, windowMs)` returns `{ count, windowStartedAt }`, starting again at 1 once the window has passed. Both counters share `incrementFixedWindowCount` (`@shinefold/db/utils/increment-fixed-window-count`).
- The per-site switch is `email_config.email_new_posts` (see [email](./email.md)), on by default.
- Monthly allowance: `monthlySendAllowance(plan, bandCeiling)` is `PLAN_MONTHLY_SENDS_PER_SUBSCRIBER` (6 on `GROWTH`, 0 otherwise) times the site's band ceiling (`SUBSCRIBER_BAND_CEILINGS`: 1,000, 2,500, 5,000, 10,000, 25,000). A site whose plan's rate is 0 but whose resolved entitlements include `NEWSLETTER` through a grant is allowed `GROWTH`'s rate (decided, owner, 2026-11-19); `getNewsletterLimits` in `@shinefold/db` applies this.
- Unsubscribing deletes the row. Deprovisioning a tenant purges its subscribers. `queries.retention.deletePendingSubscribersPastRetention(now, limit)` deletes up to `limit` pending subscribers whose last confirmation email (or, if none was sent, their signup) is more than 30 days before `now`, and returns how many it deleted; active subscribers are never touched. The worker's daily inactivity sweep runs it (see tenant-provisioning.md).
- Cookie `newsletter_unsubscribe_token` (one hour, `SameSite=Strict`, httpOnly, `Path=/api/newsletter/unsubscribe`) carries the token from the unsubscribe link to the confirm `POST`; without it the confirm lands on the invalid-link page.
- Cookie `newsletter_subscribed` (one year, `SameSite=Lax`, not httpOnly) set on subscribe and cleared on account unsubscribe, sign-in and sign-out (the site's Auth.js `signIn`/`signOut` events), so it never outlives the reader who set it on a shared browser. For a signed-out visitor, `NewsletterSubscribedGate` hides every newsletter module while the cookie is present, before hydration via an inline script. For a signed-in reader, the gate follows that reader's own subscription instead (`isReaderSubscribedToNewsletter`, pending or active hides), falling back to the cookie until the read resolves or if it fails.

## Sending a post

- **Starting** (`apps/web`, `startNewsletterPostSend`, after `POST /api/revalidate` has purged the cache): only a `create` of a `page_post` can start a send — Sanity sends an edit as `update`, an unpublish as `delete`, and a republish as `create` again, which finds the claim already taken. A starter post never starts one. Every site with a tenant row takes the claim; a site that is not sending posts (`getNewsletterSendingOffCause`) marks it `SKIPPED` with that cause as the reason — `NOT_IN_PLAN`, `SITE_INACTIVE`, `NEWSLETTER_OFF` or `SENDING_OFF` — and keeps the claim, so a republish after it starts sending emails nothing; Send emails can still send a post recorded as `NEWSLETTER_OFF` or `SENDING_OFF` once that cause is gone. A site that sends posts then `POST`s `{ tenantId, postId, claimedAt }` to the worker, signed with `WORKER_NEWSLETTER_ENQUEUE_SECRET`, a secret only that worker route accepts, so the web app never holds `WORKER_ENQUEUE_SECRET`, which every other worker route verifies. The post's own switch and publish date are read by the run, which releases the claim when the switch is off and sleeps until a future date. Any answer but `202`, a timeout (10 seconds) or a missing `WORKER_ENQUEUE_URL` or secret gives the claim back and logs (`revalidate.newsletter_send_enqueue_refused`, `_failed`, `_skipped`); a failed claim logs `revalidate.newsletter_send_start_failed`. None of it changes the webhook's response. A claim given back because the post's own switch was off stays open, so republishing with the switch on sends it. A post published before this existed has no claim; nothing was live before launch.
- `POST /api/newsletter/post-send` on `apps/worker`, signed with the enqueue secret, body `{ tenantId, postId, claimedAt }` (the claim the caller took), starts the `sendNewsletterPost` Workflow run. The run first takes a Workflow hook named for that claim; a replayed or retried enqueue finds it taken and ends, so one claim never drives two runs.
- **Before sending**, and again after every sleep, the run confirms its claim is still open: the stored claim has the same `claimed_at` and no outcome. Otherwise it ends without touching the claim. It then reads the site's off cause (`getNewsletterSendingOffCause`, so a Newsletter grant on a plan without it counts). `NEWSLETTER_OFF` or `SENDING_OFF` releases the claim and ends, so the post goes back to no claim and Send emails is offered. `NOT_IN_PLAN` or `SITE_INACTIVE` marks the claim `SKIPPED` with that cause and ends (`isOffCauseRecorded`: a cause Send emails can never clear), so a scheduled post whose site moved to a plan without Newsletter, or stopped being active, before its date is never emailed after a move back. An unknown site releases the claim. It then reads the post from Sanity (published perspective, the tenant's read token); an unpublished post, or one whose "Send to Subscribers" switch is off, releases the claim and ends. A post dated in the future records its date on the claim (`setNewsletterPostSendSchedule`, rewritten on each re-check only when the date changed) and sleeps durably until then, re-checking at least daily; no cron. A sleeping run keeps the code of the deploy that started it.
- **Gate** (once per run): a missing tenant Resend key or `NEWSLETTER_UNSUBSCRIBE_KEY` releases the claim and logs `newsletter_send.no_tenant_mail_key` or `newsletter_send.no_unsubscribe_key`. The run hands the gate the post it read. Every skip below records the post's title and date on the claim (`markNewsletterPostSkipped`), and a limit skip also records `emails_needed` (the active count), `allowance_left` and `band_ceiling` (the band the skip was measured against, which a later move up does not change). A paused site skips the post (`SITE_PAUSED`). The reputation level from `emailReputationLevel`: `WARN` and `SLOW` email the super admins (`buildNewsletterReputationAlertEmail`, with the level); `SLOW` also waits an hour between pages; `STOP` pauses the site (`pauseNewsletter`), alerts the super admins and skips (`REPUTATION_STOP`). Then the limits: the band is the paid `subscriber_band_ceiling` (the included 1,000 when null), never the band the current count falls in, since a band changes only when the owner moves it; the allowance is `monthlySendAllowance(plan, band)`, and both 80% notices use the same base. More active subscribers than the band skips `OVER_SUBSCRIBER_BAND`; this post's sends on top of the month's would pass the allowance skips `OVER_MONTHLY_ALLOWANCE`; either emails the owner that post emails are paused, naming the post. A send the gate lets through records its start (`recordNewsletterPostSendStart`: title, date and the active count as `recipient_count`), then reaching `NEWSLETTER_LIMIT_NEAR_RATIO` of either limit emails the owner. Each owner notice is claimed once per kind per month before it is sent and given back if the send fails. A post skipped for a limit can be sent later only with Send emails (below). Two posts gated at the same moment can together pass the allowance.
- **Sending** pages through `listActiveSubscribers` 50 at a time (each page a durable step), two sends a second, re-checking before each page: a site an operator has paused ends the run recording `SITE_PAUSED`; one that stopped sending posts ends it recording `NOT_IN_PLAN` or `SITE_INACTIVE`, or `SITE_PAUSED` for `NEWSLETTER_OFF` and `SENDING_OFF`, so a post stopped part-way is never offered Send emails (`readPageStopReason`); a reputation `STOP` pauses the site and ends the run recording `REPUTATION_STOP`. The workflow carries the running total of subscribers reached and each page writes it (`setNewsletterPostSendProgress`), so the Studio's "Sending… n of m" grows page by page and equals the recipient count once the post is sent. Each email is `buildPostEmail` from the tenant account with the site tag, the site's heading and body fonts and its dark palette (`resolveTenantEmailDarkBrand`) for dark-mode clients, the post's title as subject, `routes.post(slug)` on the site's primary domain, a signed unsubscribe link in the site's default language, and the summary headed by that language's fixed `blogPostPage.postSummary.button` label ("Summary"), which the caller resolves and passes as `summaryHeading`; its Resend idempotency key is `<postId>:<subscriberId>`, never empty and under 256 characters. A send Resend may accept later (`isRetryableSendError`: a network failure, a 429 or a 5xx) fails the page step so Workflow retries it, and the key keeps the retry from emailing anyone twice; a send that can never succeed is logged (`newsletter_send.send_failed`) and skipped. Resend keeps a key for 24 hours, so the run's own record is each finished page, which Workflow stores durably: a run resumed later continues after its last finished page. Each page's sends are added to the day's `NEWSLETTER_ISSUE` count in a step of their own, so a retried page is not counted twice. An address that will not decrypt is counted, and the run logs the total once (`newsletter_send.subscribers_unreadable`); a page where no address decrypts (a wrong keyring) fails the run with one `newsletter_send.page_unreadable` line. The last page marks the post `SENT`. A run that fails for good — a step out of retries or a fatal error, at any point from the first check on — settles its claim `FAILED` (`failNewsletterSend`, through `markNewsletterPostFailed`) and logs `newsletter_send.run_failed` once with the claim's `reachedCount` and `recipientCount` (both absent when it failed before the gate recorded its start). A failed claim is never released or offered Send emails, since that would email again the subscribers the run already reached.
- **Sent by hand** (Send emails): the platform clears or takes the claim (`startNewsletterPostSendByHand`) and `POST`s its new `claimedAt` to the same worker route. The run is a first publish with one difference: with `hand_started_at` set, the post's own switch is not checked. The off-cause read, the mail key, the post being published and the gate all run as usual, so a hand send the gate refuses is skipped with the gate's reason, title and date and sends the paused owner email under the same once-a-month rule, and one the check step cancels releases its claim, which takes `hand_started_at` with it and offers Send emails again.
- **Owner emails** (`sendOwnerNewsletterNotice`, copy in every owner locale under `apps/worker/src/utils/owner-email/owner-newsletter-email-copy/`): band near, emails near, and paused, whose band and emails variants share the `SENDING_PAUSED` kind, so at most one paused email goes out a month. Each shows a usage box — both limits in a near email, only the one hit in a paused one — and its button opens `/dashboard/subscribers`. The paused email names the skipped post and says it can be sent with Send emails once the cause is gone. The closing line prices the next band from the Stripe catalogue (`listStripePrices`, `bandKeyFor`) for the tenant's stored `billing_interval` and `billing_currency` — `bandMoveUpFor` from `@shinefold/db`, formatted with `formatStripeAmount`, "a year more" on yearly; a catalogue read that fails logs `newsletter_send.move_up_price_failed` and drops only the move-up sentence; the 25,000 band, a site with no stored interval or currency, and one with no catalogue price in its currency get no move-up sentence.

## Constraints and invariants

- A malformed email answers `INVALID` with `fieldErrors` for `email` before any tenant lookup, write or send.
- Most restrictive wins: the module renders only when the resolved entitlements (plan and open grants) include `NEWSLETTER` and the toggle is on, and `subscribeToNewsletterAction` re-checks the capability and refuses with `UNAVAILABLE`.
- A suspended site renders no signup form (`isRequestTenantActive`), and shows it again on the first page load after reactivation. Subscribe and confirm write only through `resolveWritableTenant`; an inactive tenant gets the no-retry "unavailable" copy. Unsubscribe by link resolves the tenant without the active check, so it works for any tenant on any plan.
- At most one row per tenant and address at a time (`Reader@` finds the row stored for `reader@`; a `+tag` address such as `reader+news@` is a separate subscriber with its own row; unsubscribing deletes a row, so a later subscribe creates a new one); a repeat subscribe for a pending address resends the confirmation only when the last send is over 15 minutes old, and otherwise answers `SUCCESS` without email. An active address answers `ALREADY_SUBSCRIBED` without email. A failed send gives the cooldown back. Every confirmation email that is sent, from a signup or from `/account`, mints a fresh random confirm token and stores its hash only once the send succeeds, so a failed send leaves the previous confirm link working and a successful one retires it; incoming confirm tokens are hashed before the lookup. The unsubscribe link never changes: its token is `<subscriberId>~<HMAC-SHA256 of the id under NEWSLETTER_UNSUBSCRIBE_KEY>`, verified rather than stored, so the link in every email a subscriber was sent keeps working until they unsubscribe. A token that is not signed lands on the invalid-link page.
- Abuse guards run before anything is stored: Vercel BotID (`checkBotId()`; a bot is refused and logged as `newsletter.subscribe_blocked`), then a per-IP limit of 5 attempts per 10 minutes per tenant, counted in the shared rate-limit store. Both refuse with `RATE_LIMITED` and store and send nothing. When BotID itself errors, or the store errors, times out (2 seconds) or is unconfigured, sign-up fails closed with the same outcome and one `newsletter.subscribe_blocked` warn.
- Confirmation flips `PENDING` to `ACTIVE` in place; a second click shows the same confirmed page.
- Opening the unsubscribe link or the confirmation page never deletes; only the POST does.
- Link language comes from the subscribing page's locale, re-validated against the tenant's locales by `resolveNewsletterLinkLocale`.
- The from address is `NEWSLETTER_FROM_ADDRESS`, else Resend's testing sender; a tenant sender name replaces only the display name, sanitized for header injection.
