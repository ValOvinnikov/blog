# Tenant provisioning

## What it does

An operator creates a tenant in the admin. That inserts a draft row and enqueues a provisioning run on `apps/worker`, which gives the tenant everything it needs:

- its own Sanity project and dataset;
- starter content;
- read and write tokens;
- a domain on the shared web Vercel project;
- a revalidation webhook.

The run then verifies all of it. The admin polls each step's progress and offers Retry. Deprovisioning reverses the run: it archives the tenant, never hard-deletes it. Reactivation re-runs provisioning. Deletion is a separate, final hard delete of an archived tenant.

## Surfaces and routes

- **Operator pages (any `admins` row):**
  - `/tenants` lists tenants, with an archived toggle.
  - `/tenants/new` is the add-tenant wizard.
  - `/tenants/{id}` shows an overview with a provisioning banner. Its Domain card has the title and a DNS link in its header, then rows for Status (the verification pill), Public domain and, when Vercel reported a status, Last checked.
  - `/tenants/{id}/provisioning` shows each step's status and the run. Until the workflow starts the run, it says the run is queued and counts the wait. A step that finishes between two polls is still shown Running before it settles.
  - `/tenants/{id}/domain` shows a Your domain card with live Vercel verification. Until the domain verifies it shows the address and lists the DNS records to add; once verified it shows the address with a Visit site link, its status, when it was last checked, whether it is a platform address (under `TENANT_ROOT_DOMAIN`) or a custom domain, and that HTTPS is active.
- **SUPERADMIN only:** `/tenants/{id}/danger` holds deprovision (with dry run), reactivate and delete.
- **Owner:** `/dashboard` shows a setup progress card, with Retry on a failure and Start setup when the first run never started (PENDING, every step idle), until provisioning is READY. Both call the same retry action, whose worker guard refuses a second concurrent run. Its Domain card has the same header and rows as the operator Overview's. `/dashboard/domain` shows the same domain view.
- **Workflows:**
  - `deprovision-tenant.yml` and `invalidate-tenant-cache.yml` are dispatch only. No workflow provisions a tenant.
  - `recheck-tenant-owners.yml` and `validate-tenant-documents.yml` are dispatch only while their crons are parked.
- **Worker:** `apps/worker` (`worker-dev`/`worker-prod`, no public hostname) serves `POST /api/provision`, body `{ "tenantId": "<uuid>" }`. It is signed with `x-worker-timestamp` (epoch milliseconds, within 5 minutes of the worker's clock) and `x-worker-signature` (`sha256=` plus the hex HMAC-SHA256 of `<timestamp>.<request path>.<raw body>`, keyed with `WORKER_ENQUEUE_SECRET`). It answers 202 with the run id, 401, 400, 404, or 409 when a run is already in progress. `POST /api/owner-access/check` ("Check now") and `POST /api/owner-access/resend` take the same signed body, plus an optional `formerOwnerEmail` that only the resend reads, and answer 202, 401, 400, 404, or 409 `NOT_PROVISIONED` while the tenant has no Sanity project. The admin panel's "Add tenant", retry and reactivate call `POST /api/provision`; the owner's Studio explainer calls the owner-access routes. `POST /api/deprovision` takes the same signed body, starts a deprovisioning run and answers 202 with the run id, 401, 400 or 404. Nothing calls it yet; the inactivity sweep starts the same run itself. `POST /api/custom-domain/connect` and `POST /api/custom-domain/disconnect` take the same signed body plus a `domain` (trimmed, lower-cased, `DOMAIN_PATTERN`) and answer 202 with the run id, 401, 400 or 404. Connect adds the domain to the shared web project (`connectCustomDomain`, idempotent, never waiting on DNS); it refuses an archived tenant with 404, a tenant without a Sanity project with 409 `NOT_PROVISIONED`, and a domain whose `tenant_domains` row does not belong to the tenant with 409 `DOMAIN_NOT_ASSIGNED`, so the caller writes the row first. Disconnect removes it (`disconnectCustomDomain`, a host already gone counts as removed) and refuses with 409 `DOMAIN_STILL_ASSIGNED` while any tenant, archived or not, still holds the domain as a `tenant_domains` row or as its `primaryDomain`, and with 409 `DOMAIN_RESERVED` for the web or platform app's own host (answering 500 when `WEB_APP_URL` or `PLATFORM_APP_BASE_URL` is unset), so the worker never pulls a host that still routes; it accepts an archived tenant. Each run's step re-checks the row before touching Vercel. The guard is best effort, with no lock between the check and the Vercel call, so the caller writes the row before connecting and deletes it before disconnecting; a failure after its retries is logged (`custom_domain.connect_failed` / `custom_domain.disconnect_failed`) with no operator alert. Nothing calls either route yet. The worker has two cron routes, both called by Vercel Cron (`apps/worker/vercel.json`) with `Authorization: Bearer <CRON_SECRET>`. `GET /api/inactivity-sweep` runs daily at 06:17 UTC and answers 200 with the number of tenants each stage advanced, 401 for any other secret, and 500 when `CRON_SECRET` is unset (logged `inactivity_sweep.not_configured`) or the sweep cannot run (`inactivity_sweep.failed`). `GET /api/owner-access-sweep` runs hourly at minute 41, with the same 300-second function limit as the inactivity sweep, and answers 200 with `{ checked, failed }`, 401 for any other secret, and 500 when `CRON_SECRET` is unset (`owner_access.sweep_not_configured`) or the tenant list cannot be read (`owner_access.sweep_failed`).
- **Manual CLIs:** `db:seed-tenant` and `db:recover-wedged-provisioning`.
- **Break-glass CLI:** `pnpm --filter worker provision-tenant -- --tenant-id=<uuid>`, run with the worker's env, provisions one tenant when the worker deployment cannot. It runs the same units in the same order behind the same `beginTenantProvisioning` guard, but once: no durable retries, so a unit's first failure marks its step FAILED. It never starts owner access and logs `provisioning.cli_owner_access_not_started`; a signed `POST /api/owner-access/check` starts it. Its run id starts `cli-`.

## Data

- **Provisioning state on `tenants`:**
  - `provisioningStatus` is PENDING, PROVISIONING, READY or FAILED.
  - `provisioningSteps` is jsonb, one entry per step (IDLE / RUNNING / DONE / FAILED with error and `updatedAt`), plus a `run` entry: `startedAt`, `finishedAt`, `admittedAt`, `registry` and `workflowRunUrl`.
  - Artifacts: `sanityProjectId`, `sanityDataset`, both encrypted tokens, `seededAt` and `webhookCreatedAt`.
  - `sanityManagementTokenEncrypted` and `sanityManagementRobotId`: the tenant's management token, a `developer` robot on its own Sanity project, and that robot's id. The token is encrypted with `TENANT_TOKEN_ENCRYPTION_KEY` like the read and write tokens; both are written by `setTenantSanityManagementToken` and read with the project id by `getTenantSanityManagementCredentials`. `SANITY_PROJECT` mints it once the project exists; `REVOKE_SANITY_TOKENS` revokes it last, found by its robot id, and `CLEAR_ARTIFACTS` nulls both with the other tokens. A tenant provisioned before either existed is re-provisioned, not backfilled.
  - Robot token labels: every robot the worker mints is labelled from the worker's `PRODUCT_NAME` env var (`buildSanityTokenLabels`): the management token carries the name itself, the read and write tokens `<name> web-read` and `<name> web-write`. Provisioning fails while `PRODUCT_NAME` is unset.
  - `lastNotifiedOwnerElevationOutcome` and `deprovisioningSteps` (same shape as `provisioningSteps`).
  - `siteType` (`SITE_TYPE`: BLOG, PORTFOLIO, PERSONAL, DOCS, BLANK, BUSINESS, PRODUCT; a `site_type` pgEnum, null for tenants created before signup) and `siteTemplateVersion`.
  - `selfServeOwnerEmailIndex`: the owner's normalised-address hash on a tenant created by self-serve signup, null otherwise, under the partial unique index `tenants_self_serve_free_owner_idx` that allows one FREE, non-archived self-serve tenant per person ([Platform sign-in and onboarding](platform-sign-in-and-onboarding.md)).
  - Owner Studio access: `ownerSanityInviteId`, `ownerInviteSentAt`, `ownerInviteAcceptedAt`, `ownerSanityUserId`, `ownerLoginProvider` (`SANITY_LOGIN_PROVIDER`), `ownerSanityRole` (`SANITY_PROJECT_ROLE`) and when each owner email went out (`ownerInviteHeadsUpSentAt`, `ownerInviteNudgeSentAt`, `ownerSiteReadySentAt`), read and written through `getTenantOwnerAccess` / `setTenantOwnerAccess`. The worker claims each sent-at atomically with `claimTenantOwnerEmail` (`TENANT_OWNER_EMAIL`) before sending, and `releaseTenantOwnerEmail` clears its own claim after a failed send.
  - Inactivity lifecycle: `lastActivityAt` (set at creation; rows that existed before the column took the migration's time), `inactivityWarnedAt`, `suspendedAt`, `deletionNotifiedAt` and `suspensionReason` (`SUSPENSION_REASON`: INACTIVITY or OPERATOR). `touchTenantActivity` moves `lastActivityAt` forward (never back) and clears the warning and deletion-notice stamps; it refuses an archived tenant. `apps/web`'s Sanity revalidate webhook (`/api/revalidate`) calls it for every signature-verified delivery from a resolved, non-archived tenant, so publishing in a tenant's Studio counts as activity; a failed touch is logged (`revalidate.tenant_activity_touch_failed`) and never fails the revalidation. `listTenantsDueForInactivityStage(stage, now)` returns the tenants due at an `INACTIVITY_STAGE` — SUSPENSION_WARNING (day 23, ACTIVE, not yet warned), SUSPENSION (day 30, ACTIVE, warned), DELETION_NOTICE (day 50, SUSPENDED for INACTIVITY, not yet notified) and DEPROVISIONING (day 60, notified, no deprovisioning run started since the notice) — never an archived one. `stampTenantInactivityStage(tenantId, stage, now)` re-checks that the tenant is still due and stamps it in one conditional update, returning the row only to the caller that claimed it; SUSPENSION also sets `status` SUSPENDED and the reason INACTIVITY. The deprovisioning stage is claimed by `startDeprovisioningRun`, which the worker's deprovisioning run records at its start. The worker's owner-access check calls `touchTenantActivity` with the acceptance time the first time it finds the owner has accepted their invite. The worker's inactivity sweep calls the due-list and stamp queries. `wakeTenantFromInactivity(tenantId)` returns a tenant SUSPENDED for INACTIVITY to ACTIVE and clears `suspendedAt` and the reason, returning the row only to the caller that woke it; once its deletion has started (a deprovisioning run or step recorded) it stays suspended. An operator's `setTenantSuspension` records the reason OPERATOR on suspend (overriding INACTIVITY) and clears the reason and `suspendedAt` on lift, so the sweep and a sign-in never treat an operator suspension as an inactive one.
  - Owner sign-in: every successful platform sign-in (`withOwnerSignInActivity` composed onto `buildAuthConfig(AUTH_APP.PLATFORM)`'s `events.signIn`) touches activity for each tenant the user holds an OWNER membership on and wakes any it finds suspended for inactivity, purging that site's cache through `revalidateSiteConfig`; an OPERATOR suspension stays. Failures are logged (`tenant.sign_in_activity_failed`, `tenant.sign_in_owner_lookup_failed`) and never block sign-in.
  - `provisioningSteps` also accepts the `apps/worker` unit keys (`WORKER_PROVISIONING_STEP`: `ENSURE_INFRASTRUCTURE`, `INVITE_OWNER`, `APPLY_SITE_TEMPLATE`, `VERIFY_TENANT`, `ENSURE_OWNER_ACCESS`, `VALIDATE_DOCUMENTS`), present only once a worker run reports them.
- **Core steps, in order:**
  1. `SANITY_PROJECT` creates the project, mints the tenant's management token, then creates the dataset, adds a CORS entry for the admin origin, and invites the owner as `viewer`.
  2. `SEED_CONTENT` writes `settings_site`, `settings_navigation`, `settings_footer`, `page_home` with its `template_home`, and `page_postIndex` with its `template_postIndex`, plus the tenant's site-type template ([Site templates](site-templates.md)), built by `@blog/config`'s `buildStarterDocuments({ siteType, siteName, locale, publishedAt })` in the tenant's default locale. A tenant with no site type, or one whose template isn't built yet, seeds Blank. Once seeded, the unit records `site_template_version` and inserts the type's `site_config` preset if the tenant has none. Each document is typed against the generated Sanity types and created with `createIfNotExists` under a fixed id, so a re-run never overwrites an owner's edits. It runs only if `settings_site` is absent, using an `editor` token that is persisted on success and revoked on failure.
  3. `PERSIST_TOKEN` mints a `viewer` read token.
  4. `MAP_DOMAIN` adds `primaryDomain` to the shared web project.
  5. `CREATE_WEBHOOK` lists the project's webhooks and creates one only when none targets `${WEB_APP_URL}/api/revalidate`. It creates the hook on `api.sanity.io`'s hooks endpoint, triggered on create, update and delete with the `{_type, _id, "slug": slug.current}` projection, then re-lists and fails, naming the project, if the hook is not there. `webhookCreatedAt` is display-only and never skips the check, so a hook at an old URL, or one deleted in Sanity, is replaced on the next run.
  6. `VERIFY_CONTENT` re-checks the singletons, nav links, the home heading and SEO title, the webhook and the domain.
- **Owner elevation:** `OWNER_ELEVATION` runs after the core steps and never changes the overall status. It records one of `ELEVATED`, `ALREADY_ADMINISTRATOR`, `PENDING_ACCEPTANCE`, `STALLED` (after 3 days) or `AMBIGUOUS_MEMBERSHIP`.
- **Deprovisioning steps:** `REMOVE_DOMAIN` (every host the tenant answers to — `primaryDomain` plus each `tenant_domains` row, through `@blog/db`'s `listTenantHosts` and `deleteVercelProjectDomains`, in both the worker and the CLI), `REVOKE_SANITY_TOKENS` (every robot on the project whatever its label, hand-made ones included, the tenant's management token last by its stored robot id, while the project is still live; a tenant whose management token has no stored robot id stops the run here and revokes nothing; one with no management token holds no robot of ours and is skipped), `ARCHIVE_SANITY_PROJECT` (sets `isDisabledByUser`), `CLEAR_ARTIFACTS`, `ARCHIVE_TENANT` (`status` ARCHIVED plus `deprovisionedAt`), `PURGE_READER_DATA` (`subscribers`, `bookmarks`, `membership_invites` and `leads`, through `@blog/db`'s `purgeTenantReaderData`; memberships, the tenant's configuration, findings and the archived row stay) and `INVALIDATE_TENANT_CACHE` (POST to `/api/revalidate-site-config`).
- **Audit:** each lifecycle event writes an `audit_events` row: created, provisioned or failed, deprovision requested, reader data purged, deprovisioned, reactivated, deleted.

## Configuration

- **Who can do what:**
  - Any admin can create a tenant and edit its name, domain, plan, language and the owner email of an owner who has not signed in yet.
  - A SUPERADMIN, or the tenant's own OWNER from `/dashboard`, can retry provisioning. Only a SUPERADMIN can deprovision, reactivate or delete. Creating a tenant (any admin) starts the first run.
- **Unknown owner email:** if the email has no user yet, the wizard requires an HMAC confirmation token. The owner then gets an OWNER invite and a magic-link email ([tenant access](./tenant-access.md)).
- **Platform env:** `WORKER_ENQUEUE_URL` and `WORKER_ENQUEUE_SECRET` sign and send each enqueue. Either missing, the enqueue is skipped and logged and the action reports a server error. `TENANT_PROVISIONING_GITHUB_TOKEN` (`actions: write`), `TENANT_PROVISIONING_GITHUB_REPO` and `TENANT_PROVISIONING_DATASET` drive the deprovisioning dispatch.
- **Worker deploy:** `deploy-development.yml`'s `deploy-worker` job deploys `apps/worker` to `worker-dev` when the worker's turbo graph changed (or on every manual dispatch); `deploy-production.yml` does not deploy the worker yet.
- **Worker env:** the provisioning secrets live on the `worker-dev`/`worker-prod` projects ([environment variables](../context/environment-variables.md)). Both cron routes need `CRON_SECRET`; the inactivity sweep also needs `PLATFORM_APP_BASE_URL`, `WEB_APP_URL`, `SITE_CONFIG_REVALIDATE_SECRET` and `TENANT_ROOT_DOMAIN`; with one missing it sends and stamps nothing. With `LOKI_PUSH_URL`, `LOKI_USER` and `LOKI_TOKEN` set, the worker ships its `warn` and `error` lines to Grafana under `service="worker"`; with any unset it logs to the console only and still runs.
- **Workflow env:** each remaining workflow resolves its secrets from the dispatched GitHub Environment: `SANITY_MANAGEMENT_TOKEN`, `VERCEL_TOKEN`, `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID_WEB`, `PLATFORM_APP_BASE_URL`, `WEB_APP_URL`, `TENANT_TOKEN_ENCRYPTION_KEY`, `OPERATOR_ALERT_SECRET`, and `TENANT_REGISTRY_DATABASE_URL` (mapped to `DATABASE_URL`).

## Constraints and invariants

- **Admission:** `beginTenantProvisioning` admits a run in one atomic `UPDATE … RETURNING`. It accepts a row that is not PROVISIONING, or one whose run is provably dead: a failed step since `startedAt`, a recorded finish, or no start recorded, or a start older than 30 minutes. A run admitted within the last 2 minutes is never treated as dead. Only the worker calls it; the admin panel maps the worker's 409 to "already in progress" and its 404 to "not found".
- **Queued run:** a run is queued while `run.admittedAt` is set and the status is PROVISIONING; the workflow's start replaces the `run` entry and drops it.
- **Overall status:** any FAILED step settles the status to FAILED. Only `VERIFY_CONTENT` finishing settles READY.
- **Timeouts:** every Sanity management and Vercel call aborts after 30 seconds, so a hung call fails its step instead of stalling the run.
- **Two Sanity credentials:** the worker uses the organisation token (`SANITY_MANAGEMENT_TOKEN`) only where a project-scoped token cannot: creating the project, minting the tenant's management token right after, unarchiving the project on reactivation, archiving it at deprovisioning (`isDisabledByUser` needs `sanity.project/update`, which `developer` lacks), listing the organisation's users while looking for the owner, and granting or removing an `administrator` role on the project's ACL — the owner's promotion and a former owner's removal — which Sanity refuses a project-scoped token (`400`, "Only a project administrator can affect administrator roles"). Every other Sanity call — dataset and CORS setup, owner invites, read and write token mint and revoke, the revalidation webhook, the ACL reads and every non-administrator role change of owner access, the seeded-content webhook check — uses the tenant's management token. A tenant without one fails that step with an error naming `sanityManagementTokenEncrypted`; re-provisioning it mints one, which only works while the organisation token is the one that created the project. The two CLIs make the same choice through the same `@blog/db` helpers (`sanityRoleChangeToken`, `robotsInRevocationOrder`): `deprovision-tenant.yml` lists and revokes every robot on the project with the tenant's management token, revoking that token last, and keeps the organisation token only to archive the project; `recheck-tenant-owners.yml` reads the ACL with the tenant's management token and keeps the organisation token only to grant `administrator`. Both read `TENANT_TOKEN_ENCRYPTION_KEY` to decrypt it. A tenant without one has its token revoke skipped and logged by `deprovision-tenant`, and fails its `recheck-tenant-owners` check; one whose token has no stored robot id stops `deprovision-tenant` at the token revoke.
- **Rotating the organisation token:** a tenant that has a management token keeps working after `SANITY_MANAGEMENT_TOKEN` is replaced. The new token is not a member of projects created before the rotation, so it cannot archive, unarchive or promote an owner on them, nor mint a management token for them: archive such a project, and promote its owner to `administrator`, by hand in Sanity Manage. `recheck-tenant-owners` counts a refused promotion as a failed check, names that step in its error and exits non-zero.
- **What a `developer` token can do:** checked on dev on 2026-10-31 against a throwaway project and a real test user. It minted and revoked an `editor` robot (`201`/`204`), so seeding uses the tenant token; it was refused `administrator` on a user (`400`), so promotion stays on the organisation token.
- **Project membership:** the organisation token is an implicit administrator only of projects it created. A tenant row pointing at a project created elsewhere, such as the shared dev project, cannot get a management token until the token's robot is added to that project as administrator.
- **Revalidate webhook signature:** `apps/web`'s `/api/revalidate` verifies a delivery from a tenant's project (by its `sanity-project-id` header) against that tenant's stored webhook secret only, so a request signed by one tenant and resent with another's project id is refused. A tenant with no stored secret is refused; only the platform's own projects, which no tenant owns, are verified against `SANITY_REVALIDATE_SECRET`. A tenant provisioned before per-tenant secrets gets one from `pnpm --filter worker rotate-webhook-secrets`, which must report no failures on an environment before a web deploy reaches it. A signature whose `t=` timestamp is more than five minutes from now is refused. Every refusal is the same 401, logged nowhere.
- **Idempotency:** every step reads state it already created and resumes; the project id is persisted the moment it is minted, since Sanity cannot delete an orphan. A retry from the status view enqueues a whole new run, not one step.
- **Worker runs:** the enqueue route admits the run through `beginTenantProvisioning`, then starts a Vercel Workflow run (`workflow`, pinned exactly to 5.x). If the start fails after admission, the run is recorded as failed (`SANITY_PROJECT` FAILED, run finished), never left PROVISIONING. The run calls four units in order: `ensureInfrastructure` (`SANITY_PROJECT`, `PERSIST_TOKEN`, `CREATE_WEBHOOK`, `MAP_DOMAIN`), `inviteOwner`, `applySiteTemplate` (`SEED_CONTENT`) and `verifyTenant` (`VERIFY_CONTENT`). It reports under the same six step keys, so the status view is unchanged. A failing unit is retried up to three times and the run resumes from it, never from the start; after the last attempt the step is FAILED. The owner invite runs inside the `SANITY_PROJECT` step; `inviteOwner` then records that invite's id and sent-at, sending one only if the owner has none, and never fails the run. Document validation is not a worker unit, since the validator needs the Sanity CLI and the Studio source, which a Vercel function lacks; a fresh tenant holds only the starter documents, which `starter-content.test.ts` validates, and `validate-tenant-documents.yml` stays a manual drift check. Audit events carry the actor `worker`.
- **Owner Studio access (worker):** a successful worker run starts `ensureOwnerAccess`, a separate Workflow run per tenant (hook token `owner-access:<tenantId>`). Each check finds the owner among the project's users by email (Access API `/access/project/{id}/users`); an owner who is already a user of the Sanity organization is added to the project as `viewer` directly, with no invite. A found owner is granted `administrator` through the project ACL (on every plan for now), whose entry is keyed on the user's project membership `resourceUserId`, falling back to their profile id, and every other role on that entry, such as the invite's `viewer`, is then removed, so the owner holds `administrator` alone. Every check that finds the owner then deletes the owner's pending invites, matched by email, and clears the recorded invite id when it was one of them, so Manage shows no stale invitation and Sanity sends no further invite email; invites to other addresses are left alone. A failed delete is logged (`owner_access.invite_delete_failed`) and never fails the check or undoes the grant. Only Check now retries it, since a granted tenant leaves the sweep; the invite can also be cancelled in Manage. The outcome is ELEVATED unless the owner already held `administrator` alone, so a grant whose role removal only succeeds on a later check still reports ELEVATED; a found owner with no ACL entry yet is retried on the next check and their acceptance time, Sanity user id, login provider and role are recorded. A run checks every minute, at most 30 times, then ends still pending; it ends earlier at a grant, at STALLED (no acceptance three days after the invite was sent, else the tenant's creation) or at a check that still fails after its retries, such as during a Sanity outage. A failed check ends the run; it is logged and reported as PENDING_ACCEPTANCE or STALLED, and the next hourly sweep retries it. A run stays on the deployment that started it, so no run outlives a deploy by more than about 30 minutes. The hourly owner-access sweep (`runOwnerAccessSweep`) lists every ACTIVE, READY tenant whose recorded owner role is not administrator and makes one check for each on the current deployment: it wakes a live run, and starts a one-check run when none is live. Before waking, any live run older than 45 minutes (one and a half times a run's 30 checks) is cancelled, since it can only have started on an earlier deployment, and a fresh run is started on the current deployment in its place; Check now, Resend and the provisioning run's start do the same. A tenant the sweep cannot check is logged (`owner_access.sweep_tenant_failed`) and the sweep carries on. The `OWNER_ELEVATION` step records when checks started failing (`failingSince`), and the next check that succeeds clears it. A single failed check opens nothing; once checks have kept failing for 30 minutes, each failed check opens or refreshes the tenant's one `OWNER_ACCESS_CHECK_FAILED` finding, whose details hold the last error, the failure count, the first failure time (`failingSince`) and the last; the grant resolves it. While no invite has been recorded, for example because `inviteOwner`'s send failed, each check sends one and records its sent-at. STALLED posts the `OWNER_ELEVATION` operator alert once, deduplicated on `lastNotifiedOwnerElevationOutcome`. Each check reports under the `OWNER_ELEVATION` step with the same outcomes, so the platform banner is unchanged. "Check now" wakes the running checks, or starts new ones once they have stopped; Resend revokes the owner's pending invites, sends a new `viewer` invite, records it and restarts the checks. Saving a changed owner email on a tenant that has a Sanity project triggers the same resend, under the details form's own admin check. When the recorded invite or Sanity user, or the request's `formerOwnerEmail`, belongs to another address than the current owner email (the owner email was changed), Resend first revokes that address's pending invites, removes every project role it holds through the project ACL (matched the same way), and clears the recorded invite id, acceptance, Sanity user id, login provider and role. Addresses compare trimmed and lower-cased. A recorded Sanity user who is no longer in the project has their Sanity user id, login provider and role cleared. The parked recheck cron stays until #5596 retires it.
- **Owner emails (worker):** the owner receives three emails from the platform, each at most once per invite. The invite heads-up goes out when the Sanity invite is recorded. The nudge goes out on the first check at least 24 hours after the invite (`ownerInviteSentAt`) while the owner still has not accepted. Site ready goes out when a check grants access (ELEVATED or ALREADY_ADMINISTRATOR); it links to the Studio, and the nudge links to the dashboard. Each is sent through `@blog/email`'s owner templates with fixed transactional copy in the site's default language (`tenants.locale`), from `OWNER_EMAIL_FROM_ADDRESS`. A resend clears the heads-up and nudge sent-ats as it records the new invite, so the owner gets a fresh heads-up and the nudge restarts from the new `ownerInviteSentAt`. A send first claims its sent-at column with a conditional update, so overlapping checks or a retried step never send twice. A failed send is logged (`owner_email.send_failed`), releases its claim and never fails the step; a pending check retries a heads-up that has not gone out.
- **No direct invite link:** Sanity's Access API returns no link or token for accepting an invite. Creating, listing and reading an invite return its id, status, role, email and timestamps only. The public `inviteToken` that the accept endpoint (`/access/project/{id}/invites/token/{inviteToken}/accept`) takes appears only in the invite email Sanity sends, so the worker cannot hand the platform a link, and the owner opens that email to accept.
- **Starter content is schema-valid:** `packages/studio/src/starter-content.test.ts` builds the Blog and Blank starter documents and runs Sanity's own document validation (`@sanity/validation`) against the schema the real Studio config compiles, once per default language in `LOCALE_ISO_CODES`, and fails on any marker. It runs in `pnpm verify` and CI, so an invalid starter document is caught before any tenant is seeded with it. Drift in a tenant's content after creation is `validate-tenant-documents.yml`'s job.
- **Worker deprovisioning:** the `deprovisionTenant` Workflow run takes the same seven steps in the same order as the CLI, each a durable step retried up to three times and reported under its `deprovisioningSteps` key, so an automatic deprovision leaves exactly what an operator's does. It skips an already-deprovisioned tenant without writing anything. Each step decides from what exists: a domain already gone, a project already archived, a row already archived or reader data already purged is done, not an error, and a failed token revoke is logged (`deprovisioning.token_revoke_failed`) without stopping the run, as in the CLI. It has no dry run and no name confirmation; the enqueue signature is the guard. After a successful run, every SUPERADMIN gets one email naming the archived Sanity project and linking to it in Sanity Manage, because only Manage can delete a project. The worker sends it itself through `@blog/email`'s `buildArchivedSanityProjectAlertEmail`, from `OPERATOR_ALERT_FROM_ADDRESS`; a tenant that never got a project sends none. Audit events carry the actor `worker` and `via: deprovision-tenant-worker`.
- **Inactivity sweep (worker):** a tenant with no activity — no owner sign-in to the platform, no Studio publish, no invite acceptance — moves through four stages, counted in days from `lastActivityAt`. Day 23: the owner gets the pause warning and every SUPERADMIN gets its English copy. Day 30: the tenant is suspended for INACTIVITY and its site cache is purged, so the next page load serves the suspended site. Day 50: the owner gets the deletion notice. Day 60: the sweep starts the `deprovisionTenant` run and records its start. The sweep visits the stages latest first, so a tenant moves at most one stage per sweep even after a missed day. Each stamped stage is claimed with `stampTenantInactivityStage` before anything is sent, so a second sweep the same day, or an overlapping one, sends nothing twice; a claimed stage whose send fails is logged (`inactivity_sweep.email_send_failed`) and not retried. A tenant with no owner is stamped and logged (`inactivity_sweep.owner_missing`) and gets no email. A failing tenant is logged (`inactivity_sweep.stage_failed`) and the sweep carries on with the next. The owner emails use fixed copy in the site's default language (`tenants.locale`, `OWNER_INACTIVITY_EMAIL_COPY`), with the pause or deletion date written in that language, and a sign-in button to the admin dashboard; they come from `OWNER_EMAIL_FROM_ADDRESS`, and the SUPERADMIN copy from `OPERATOR_ALERT_FROM_ADDRESS`. The platform tenant — the one whose hosts include `TENANT_ROOT_DOMAIN` or its `www.` host (`isPlatformTenant`, `@blog/db`) — is never warned, suspended or deprovisioned; the sweep skips it at every stage and logs the skip once per run (`inactivity_sweep.platform_tenant_skipped`). Activity at any stage resets the clock: `touchTenantActivity` clears the warning and deletion-notice stamps, and a sign-in wakes a tenant suspended for inactivity until its deprovisioning has started.
- **Retention cleanups (worker):** the same daily run, after the stages, deletes personal data past its retention period through `queries.retention.*`: pending newsletter subscribers 30 days after their last confirmation email, contact leads 12 months after they arrive, expired sessions and sign-in tokens, audit events after 24 months, and resolved findings 90 days after resolution. Each cleanup deletes in batches of `RETENTION_DELETE_BATCH_SIZE` (1,000) rows per statement, repeating until a batch comes back short, so a first run on a large table is never one long statement. No batch starts after `RETENTION_RUN_DEADLINE_MS` (240s) from the sweep's start, a minute inside the route's 300s `maxDuration`; a kind cut short or never reached is listed in one `retention.deadline_reached` warning and finishes on later days. It logs one `retention.deleted` line with the count per kind, including what a cut-short run deleted. A failing cleanup is logged (`retention.cleanup_failed`) and the others still run, and the cleanups run even when the stages fail. The response carries `{ advanced, deleted }`.
- **No hard deletes:** deprovisioning only archives. It defaults to a dry run, and `confirm` must equal the tenant's name; the workflow checks that again. An already-deprovisioned tenant is skipped, so a failed cache purge is retried through `invalidate-tenant-cache.yml`. The CLI refuses the platform tenant (`isPlatformTenant`) before any step and exits non-zero naming the reason; it needs `TENANT_ROOT_DOMAIN`, so with it unset it refuses every tenant. The admin refuses it too: the Danger page shows a notice saying why in place of Deprovision, and `deprovisionTenantAction` returns `PLATFORM_TENANT` without dispatching and logs `tenants.platform_tenant_refused`.
- **Delete:** delete refuses a tenant that is not archived. It hard-deletes the row and cascades. No Sanity token is passed, so the archived project is left in place.
- **Locked fields:** details lock once provisioning is RUNNING or SUCCEEDED, except the owner email, which stays editable after success until the owner first signs in ([tenant access](./tenant-access.md)); the server accepts a post-provisioning change to the owner email alone. After a failure, only `primaryDomain` locks, and only once `MAP_DOMAIN` is DONE. Separately, `primaryDomain` locks whenever the main address is a custom domain (not under `TENANT_ROOT_DOMAIN`), and the server refuses a change with `DOMAIN_CUSTOM_MAIN`; switching back to the subdomain on the Domain page unlocks it. With `TENANT_ROOT_DOMAIN` unset, every host counts as a custom domain, so the field stays locked; that is a misconfiguration the lock fails safe on.
- **Draft rows:** a draft tenant is ACTIVE with PENDING provisioning. Its domain row exists from creation, so the [multi-tenancy](./multi-tenancy.md) read gate (READY in production) keeps it dark until the run succeeds.
