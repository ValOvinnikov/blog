# Billing

## What it does

A site with no live subscription (Free, a trial, a lapsed site) buys Starter or Growth on the Upgrade page, inside the platform, through Stripe's Embedded Checkout; a paying site changes its plan or billing period on the same page by updating its one subscription. Stripe is the source of truth for a paying site's plan and status. A Stripe webhook keeps each tenant's `plan`, `status`, Stripe ids, promotion code, subscriber band and downgrade grace in step with its subscription, and sends the owner our own receipt for each paid invoice. Stripe's own customer emails stay off. The owner sees the plan, the next payment and every invoice on a Billing page inside the platform, and changes the card or cancels through Stripe's hosted Customer Portal.

## Surfaces and routes

- `POST /api/stripe/webhook` (`apps/platform`) — public, outside the locale proxy. It verifies the `stripe-signature` header against `STRIPE_WEBHOOK_SECRET` with the Stripe SDK on the raw body, refusing a missing or wrong signature with 400 and changing nothing. Either secret unset answers 500 and logs `billing.webhook_secret_missing`. A handler failure answers 500 (`billing.webhook_handler_failed`) so Stripe retries; everything else answers 200.
- `/dashboard/billing` (`apps/platform`) — the Billing page, for the site's real owner and a super admin only (`viewer.isOwner || viewer.isSuperAdmin`): the sidebar's Account section links it only for them (`resolveTenantPageAccess` → `billing`), and anyone else — an editor, a moderator or another admin role — gets a 404 (`resolveGatedDashboardTenant('billing')`, the same resolver Leads uses). A super admin sees it read-only — plan, status, next payment and invoices, with no Manage billing — for support; an operator who has to act on a customer's billing uses the Stripe dashboard.

## Billing page

- The header renders at once; the Stripe reads stream in under a skeleton. `PageHeader` carries **Manage billing** for the site's real owner (`viewer.isOwner`) whenever the site has a Stripe customer.
- **Plan card:** the plan name and the tenant's status badge, and the next payment as "{amount} on {date}" (the date in a `<time>`). The next payment needs a stored subscription id: the subscription is read first (`previewRenewal`), and only a live one (`active`, `trialing`, `past_due`) that is not cancelling is previewed with `invoices.createPreview` (dated by `next_payment_attempt`, else the invoice's date). A live subscription counts as cancelling when either `cancel_at` (what the Customer Portal's cancel sets) or `cancel_at_period_end` is set (`subscriptionEndsAt`); the card then drops the next-payment row and reads "Your plan ends on {date}" (`cancel_at`, else the plan item's `current_period_end`, in a `<time>`), and has no footer link, so it offers no Change plan. Undoing the cancel in the Portal clears both fields, which brings the next payment and Change plan back. An ended subscription never counts as cancelling, so a lapsed cancel reads "None scheduled" and keeps its Upgrade link. Otherwise, or when Stripe has no upcoming invoice (`invoice_upcoming_none`), it reads "None scheduled". A failed preview also reads "None scheduled", keeps the invoice list, and logs `billing.next_payment_failed`.
- **Invoices table:** every finalised invoice for the customer, newest first (`invoices.list` at Stripe's page size of 100, so one request lists eight years of monthly invoices): date, total in the invoice's currency (zero-decimal currencies formatted by their own minor units), status (Paid, Due, Unpaid, Cancelled) and a "View invoice" link to `invoice_pdf`, or the hosted invoice page when there is no PDF; its accessible name adds the date and amount, since a proration invoice can share a regular one's date. Drafts are left out.
- **No Stripe customer** (a trial, or Free that never paid): the plan card shows the plan and "Your site has no payments yet." and no table.
- The plan card's footer links to Upgrade: "Change plan" for a site with a live subscription (`hasStoredSubscription`), "Upgrade" (Checkout) for any other; a cancelling subscription has no footer.
- **Stripe unreachable or unconfigured:** an error notice in place of the cards when the invoice list cannot be read, logged `billing.overview_failed` or `billing.stripe_unconfigured`.
- **Manage billing** (`openBillingPortalAction`) re-checks the caller with `requireTenantOwner(tenantId)` — the site's real owner only; any other caller, a super admin included, 404s before a portal session is created — creates a Customer Portal session for the stored customer with `return_url` `PLATFORM_APP_BASE_URL` + `/dashboard/billing`, and redirects to it. No customer, or an id that is not a site → refused (`NO_CUSTOMER`); no key or base URL, or a failed session → a toast, logged `billing.stripe_unconfigured` / `billing.portal_failed`. The Portal's features (payment method, cancellation) and branding are set in the Stripe dashboard.
- Cost: per Billing page view, one Stripe read for the invoices plus two (the subscription, then the preview) for a site with a live subscription; one per Manage billing click; free.

- Every tenant admin page (`apps/platform`, the `(tenant)` layout's notice slot) — the billing status notice; see Behaviour.
- `/dashboard/upgrade` (`apps/platform`, owner tree) — Upgrade. The Growth note's "Ask about Growth" on Look and Sign-in links here. `?promo=<code>` applies a promotion code; without one, the code a visitor arrived at `/signup?promo=<code>` with applies instead. `?session_id=` marks the return from Checkout.

## Behaviour

### Billing status notice

- `BillingStatusNotice` streams into the tenant layout's notice slot, under the suspension banner, so it shows on every tenant admin page. Its copy is fixed platform copy in the five catalogues (`billingStatusNotice`), never Voice, and it never reads Stripe.
- **Past due** (`PAST_DUE`): "Your last payment failed. Update your payment method to keep {plan}." with **Update payment method** linking to Billing. No date: the plan is kept through `PAST_DUE` and nothing is scheduled to lock until Stripe gives up and the grace starts. Shown only to Billing's audience, the real owner and a super admin (`access.billing`); anyone else sees nothing (decided, owner, 2026-11-13).
- **Downgrade grace** (a stored `downgrade_grace_started_at`, not archived): shown to every member. It names only what applies, decided by the same rule the sweep uses, `findGraceLocks` from `@shinefold/db` ([plans and entitlements](./plans-and-entitlements.md)), which `loadGraceLocks` applies to the loaded tenant's `entitlements` and hosts: the memberships over the plan's seats, and, on a plan without `hasCustomDomain`, a custom main address and the subdomain it will redirect to. Without `TENANT_ROOT_DOMAIN` no grace notice shows. Each line carries the grace's end date (`graceEndDate` from `@shinefold/db`, the date the worker's emails print) in a `<time>`. The viewer who can upgrade (`upgradeStateFor` is `AVAILABLE`) gets **Upgrade** to the Upgrade page; any other member reads that the site owner can upgrade. A grace with nothing to lock or redirect shows no notice, as the day-7 and day-13 emails are skipped.
- The notice goes as soon as the grace ends, early or at day 14: an upgrade or a paid invoice clears `downgrade_grace_started_at` through the plan change, and the next page load renders nothing.
- Cost: none outside a grace or `PAST_DUE`; in a grace, one tenant-hosts read and one membership count per admin page load.

### Upgrade

- What the page shows comes from the tenant row alone (`upgradeStateFor`), in this order, and never from a plan name: a live subscription (a stored subscription id on a plan in `SELLABLE_TENANT_PLANS`; the webhook keeps a cancelled subscription's id and moves the site to Free) → the plan change below for the real owner of a running site (`planChangeRefusalFor`), and "Your site is on {plan}" with a link back to Overview for any other member; a member who is not the real owner (an operator's virtual membership included) → only the owner can upgrade; an archived, suspended or deprovisioned site → unavailable until it runs again; anything else → Checkout. Trial → Starter, trial → Growth and Free → either are the same flow. A paying site never sees Checkout, and a trial or Free site never sees the plan change. The Growth note's "Ask about Growth" therefore reaches the plan change on a paying site. The operator cannot change a paying site's plan either: the tenant details panel locks Plan while the site has a live subscription, so the next `customer.subscription.updated` never overwrites an operator's edit ([plans-and-entitlements](./plans-and-entitlements.md)).
- The platform loads a tenant once with its trial state: `requireTenantMembership`, `resolveDashboardTenant` and `requireTenantById` return `toPlatformTenant(tenant)`, which adds `trial` from `trialFor`, and consumers read `tenant.trial`. The webhook, the worker and `apps/web` keep raw rows.
- Checkout is Stripe's Embedded Checkout (`ui_mode: 'embedded_page'`) mounted in a card with a plan choice (`SELLABLE_TENANT_PLANS` from `@shinefold/config`: Starter, Growth; a trial's own plan, else Growth, is preselected) and a Monthly/Yearly choice; switching either, or Try again after a failure, starts a new Checkout Session. Each mount calls `createUpgradeCheckoutAction`, which re-checks the state on the server and refuses with that state's code, validates the plan against `SELLABLE_TENANT_PLANS` (anything else, Free included, is `INVALID`), then:
  - gives the site one Stripe customer (`ensureStripeCustomer`): the stored `stripeCustomerId`, or a new one created with the idempotency key `tenant-customer-<tenantId>` (so two tabs racing for the first checkout get the same customer), prefilled with the owner's sign-in email and stored with `setTenantBilling` before any session exists. A stored customer that Stripe has deleted or does not know is replaced by a new one, keyed `tenant-customer-<tenantId>-<old customer id>`, stored the same way and logged (`billing.checkout_customer_replaced`);
  - refuses with `PAYMENT_PENDING` when Stripe already has a live subscription for that customer (`active`, `trialing`, `past_due`), so a slow webhook never lets a second payment through, and expires the customer's other `open` Checkout Sessions so only the newest can be paid. Two tabs that load within the same few hundred milliseconds can each create a session after the other's expire step, so both stay payable; the window is narrow and accepted. `incomplete` is not counted as live, so a delayed payment method (SEPA, ACH) still pending is not refused — to be confirmed against a test-mode delayed payment;
  - creates a `subscription` session for the chosen plan's Price, the lookup key `PLAN_PRICE_LOOKUP_KEYS[plan]` names for the period, with Stripe Tax on (`automatic_tax`), the customer's address and name kept current for tax, and `client_reference_id` and the session's and subscription's `metadata.tenantId` set to the tenant.
- A signup carries its code to the first Checkout: `src/proxy.ts` (`rememberSignupPromo`) saves a well-formed `?promo=` on `/signup` (trimmed, 1–64 characters) in the httpOnly `platform-signup-promo` cookie for 30 days, through sign-in by email link or provider and onboarding, and the Upgrade page uses it when its own address has no `?promo=`. The cookie is never cleared; Stripe refuses a code that has expired or is first-time-only, and Checkout then offers its code field as below.
- A `?promo=` code that names an active promotion code is applied as the discount; otherwise, or without one, Checkout offers its own promotion-code field. When the code lookup fails, or Stripe refuses the code at session create (first-time-only, another customer's, a minimum or a product scope), the session is created again with the code field instead and `billing.checkout_promo_refused` is logged with the code. A missing Price is logged (`billing.checkout_price_missing`, with the plan and period), a failed Stripe call or a session without a client secret `billing.checkout_failed`; each shows "Checkout couldn't start." with Try again. A refusal shows its reason in a status message and no retry.
- Stripe returns the owner to `/dashboard/upgrade?session_id=…`. The page never reads the session and never writes the plan: it shows "Confirming your payment" and polls `getUpgradeStateAction` every 2 s (at most 30 checks, paused while the tab is hidden; a check in flight when the tab hides is dropped but still counts) until the webhook below has stored the live subscription. One status region carries every state: it reads "Your payment is confirmed" the moment the poll sees it, then the page refreshes; when `usePolledValue` reports it is out of checks, or one fails, it reads "This is taking longer than usual" with Check again, which refreshes and restarts the checks. Reloading, going back or abandoning Checkout therefore changes nothing; only the webhook does.
- The platform CSP allows Stripe.js and its frames: `script-src` and `frame-src` `https://js.stripe.com https://*.js.stripe.com`, plus `frame-src https://checkout.stripe.com https://hooks.stripe.com` (3D Secure), `connect-src https://api.stripe.com https://checkout.stripe.com` and `img-src https://*.stripe.com`.

### Plan change

- A paying site's owner picks a plan and a billing period with the same choice Checkout uses (`PlanChoices`). `PlanChangeSection` first reads the subscription from Stripe (`readTenantSubscriptionPlan` → `loadSubscriptionPlan`, one read expanding `schedule.phases.items.price`): its plan and period from the plan item's lookup key, its band, its renewal date (the plan item's `current_period_end`) and any change already planned. A subscription that is not `active` or `trialing` gets a note pointing at Billing instead (`NOT_ACTIVE`); a cancelling one (`subscriptionEndsAt`, as on Billing) gets the same note reading "Your plan ends on {date}, so it can't change", and the action refuses a change to either with `NOT_ACTIVE`. A failed read shows "Your plan couldn't be loaded" and logs `billing.stripe_unconfigured`, `billing.price_unknown` or `billing.plan_change_load_failed`.
- Which way a change goes comes from rank, never a plan's name (`planChangeTiming`): plans by their key order in `PLAN_ENTITLEMENTS`, periods by `BILLING_INTERVAL` order (monthly, then yearly). A move to a shorter period always waits for renewal, even when the plan moves up (owner decision on #7333: a paid year is never turned into Stripe credit). Otherwise a later plan, or the same plan on a longer period, is a move up and anything else a move down. The card says which before the owner confirms: a move up on the same period says the change starts today and the difference for the rest of the period is paid now; a move up that also changes the period (monthly → yearly) says a new yearly period starts today, paid now less the unused time on the current one. A planned change's note ("Your site moves to {plan} … on {date}") sits 12px above that line.
- `changePlanAction` re-checks the gate on the server (`NOT_SUBSCRIBED`, `NOT_OWNER`, `UNAVAILABLE`), validates the plan and period, re-reads the subscription, and then (`changeSubscriptionPlan`):
  - **move up** → `subscriptions.update` on the same subscription, swapping the plan item's Price (and a band item's Price for the new period), with `proration_behavior: 'always_invoice'` and `payment_behavior: 'pending_if_incomplete'`, expanding the latest invoice's payments and confirmation secret: Stripe charges the prorated difference now and applies the change only once that payment succeeds. When it doesn't succeed at once, Stripe holds the change as a pending update and the action reads the invoice's PaymentIntent: `requires_action` (the bank asks for 3-D Secure) with a confirmation secret returns that client secret beside `timing: NOW`; `processing` or `succeeded` reports the change as made; `requires_payment_method` is `CARD_DECLINED`; any other state, or a held change with no payment or confirmation secret to read, is logged as `billing.plan_change_payment_unknown` (with the status) and fails. A card error or any 402 thrown by Stripe is still `CARD_DECLINED`. Given a client secret, the card loads Stripe.js with the publishable key and calls `handleNextAction`, which shows the bank's step: once confirmed, it waits for the webhook like any move up; a cancelled or failed bank step, or Stripe.js failing to load or reach Stripe, says the plan hasn't changed (`PAYMENT_NOT_CONFIRMED`), and a card error after it says the card was declined. Both payment notices are announced as alerts. An unconfirmed pending update changes nothing and Stripe expires it, voiding its invoice. A planned change is released only after the update is applied: at once when the payment succeeds on the request, and otherwise by the webhook — a `customer.subscription.updated` whose `previous_attributes` carry both `pending_update` and `items` while the subscription no longer has one (an expiry clears `pending_update` alone) releases the attached schedule before the event is recorded, so a failed release is retried with the event. Nothing is released while the payment is held. On the request path it is the schedule the update returns, so a move down another tab planned meanwhile is released too. Once the update has succeeded the change shows as made: a failed release is retried once and, if it still fails, logged as `billing.plan_change_release_failed` with the schedule id for an operator to release it before renewal. A monthly → yearly move restarts the billing period, as Stripe does for any period change;
  - **move down** → a subscription schedule on the same subscription (any planned change released right before `subscriptionSchedules.create` from it, then `update`): the current phase keeps today's items to the period end, and the next phase holds the new Price for one period with `billing_cycle_anchor: 'phase_start'`, so a move to a longer period is first invoiced the day it starts, then the schedule releases. Discounts and automatic tax carry into both phases. A band item stays only when the new plan has that band, for the new period;
  - the same plan and period while a change is planned → the schedule is released, which cancels the planned change ("Keep {plan}"); with nothing planned → `UNCHANGED`. At most one change is ever pending. Releasing a schedule that is already released, cancelled or completed counts as done, and a create refused because another tab already planned a change releases that one and creates again, so a double submit ends in the same state. A schedule update refused because another tab released that schedule and planned its own change counts as done too. The button is disabled while a change is in flight or confirming.
- A missing target Price is logged (`billing.plan_change_price_missing`), any other Stripe failure `billing.plan_change_failed`; both show "Your plan couldn't be changed."
- Nothing in the flow writes the plan. A move up that changes the plan waits for the webhook the way the Checkout return does: it polls `getTenantPlanAction` every 2 s (at most 30 checks) until the tenant row carries the new plan, then refreshes; out of checks, or a failed check, it offers Check again. A period-only move up and a move down refresh at once, and the page then shows the period Stripe reports or the planned change ("Your site moves to {plan} … on {date}"). At renewal Stripe moves the subscription to the next phase and the webhook syncs the plan as for any other update.
- Cost: per Upgrade view of a paying site one Stripe read; per change one read plus one price lookup and one update (a move down: a create and an update on the schedule; a planned change adds a release), all free.

### Tenant lifecycle

Billing follows an operator's lifecycle actions. A live subscription is the one `hasStoredSubscription` reads: a stored subscription id on a plan in `SELLABLE_TENANT_PLANS` (`server/billing/tenant-subscription-lifecycle.ts`). A site without one suspends, archives and deletes without a Stripe call.

- **Suspend** (`suspendTenantAction`), once the suspension is saved, sets the subscription's `pause_collection` to `void`, so Stripe voids the invoices it would raise while the site is suspended; **Reactivate** (`liftTenantSuspensionAction`) clears it. The suspension is never refused over billing: a failed call is logged (`billing.subscription_collection_failed`, with `isPaused`), and no key is logged `billing.stripe_unconfigured`. The inactivity sweep's suspension does not pause billing.
- **Archive** (`deprovisionTenantAction`) cancels the subscription at once with `prorate: false` (no refund for the unused period) before it enqueues the worker, then moves the site to Free with `setCancelledTenantFree` (`@shinefold/db`), whatever its status, so a suspended site lands on Free too and a reactivated site comes back on Free. That write keeps the subscription id, clears the band and any downgrade grace, starts no grace and sends no plan-change email. The later `customer.subscription.deleted` event changes nothing. A subscription Stripe already reports cancelled counts as cancelled, so a retry works. A failed cancel or Free write, or no key, refuses the archive with `SUBSCRIPTION_CANCEL_FAILED` and logs `billing.subscription_cancel_failed` or `billing.stripe_unconfigured`; nothing is enqueued or audited.
- **Delete** (`deleteTenantAction`) asks Stripe for the stored customer's subscriptions and refuses with `SUBSCRIPTION_LIVE` while any is `active`, `trialing` or `past_due`. A site with no stored customer is not asked. A failed list, or no key, is a server error, logged `billing.live_subscription_check_failed` or `billing.stripe_unconfigured`.

### Webhook

- Handled events: `customer.subscription.created`, `.updated`, `.deleted`, `invoice.paid` and `invoice.payment_failed`. Each names a subscription (an invoice through `parent.subscription_details`); any other event, or an invoice outside a subscription, is answered 200 and ignored.
- The handler never trusts the event body for state: it re-reads the subscription from Stripe and derives the tenant's state from its current `status`, so a late or replayed event writes the subscription's present state, not a past one.
  - `active`, `trialing` → the subscribed plan, `ACTIVE`, and any downgrade grace ended (its start and the three grace-email stamps cleared).
  - `past_due` → the subscribed plan kept, `PAST_DUE`, following Stripe's retry schedule.
  - `canceled`, `unpaid` → `FREE`, `ACTIVE` and the band cleared; the downgrade grace starts only when the site was on a paid plan (an already-running grace keeps its start), and the daily sweep ([tenant provisioning](./tenant-provisioning.md)) runs it from there. Cancelling at period end therefore drops the site to Free when Stripe ends the subscription.
  - `incomplete`, `incomplete_expired` (a first checkout that never paid), `paused` and anything else → nothing is written, so a trial keeps its trial.
- The plan comes from the subscription items' Price lookup keys through `PLAN_PRICE_LOOKUP_KEYS` ([plans and entitlements](./plans-and-entitlements.md)): exactly one Starter or Growth plan Price, and at most one band Price, whose ceiling is stored in `subscriber_band_ceiling` (none → null, the included 1,000). The webhook never chooses a band; it records the one Stripe reports. An unknown or ambiguous set of Prices writes nothing and logs `billing.price_unknown`.
- The tenant is the one carrying the subscription's customer or subscription id (`getTenantIdByStripeIds`); with neither stored yet, the subscription's `metadata.tenantId`, which Checkout sets. Two tenants matching the two ids is logged (`billing.tenant_conflict`) and writes nothing; no tenant is logged (`billing.tenant_not_found`).
- A cancel wins over a planned change (decided, owner, 2026-11-17): when the re-read subscription is cancelling (`subscriptionEndsAt`) and still has a schedule attached — a Portal cancel on a site with a move down planned — the schedule is released (`releaseSchedule`) before the tenant is written, so only the cancel is left in Stripe. A failed release throws, so Stripe retries the event.
- A tenant that already stores a different subscription id ignores an event for a subscription that is no longer live (not `active`, `trialing` or `past_due`), logged `billing.subscription_superseded`: a late or retried event for a cancelled earlier subscription never undoes the current one. A new live subscription replaces the stored id.
- An archived or suspended site writes nothing (logged `billing.tenant_not_writable`). Writes, in order: `setTenantBilling` with the customer and subscription ids, the band, the grace fields, and the promotion code the subscription started with (a stored code is never replaced); then `setTenantPlan`, which re-checks the status, clears the Free-or-trial key on a move to a paid, running site, and returns the plan it replaced from the same `UPDATE`. Billing goes first so a failed billing write leaves the plan change for Stripe's retry to make.
- `recordStripeEvent` runs only after those writes succeed, so a failed write leaves the event unrecorded and Stripe's retry is processed. An event already recorded is synced again (the subscription's current state, so the tenant does not change) but triggers no follow-up.
- Follow-ups run after the response. When the plan write changed the plan — decided by that write, so the burst of events Stripe sends at checkout triggers it once — `onTenantPlanChange`, the one step every plan change runs, operator or Stripe, which today emails the owner the plan-change notice; alongside it, `revalidateSiteConfig` purges the tenant's cached site config so the new plan's features reach the site at once, and a failed purge is logged, never failing the webhook. On an `invoice.paid` event recorded for the first time, the receipt.
- The receipt (`buildOwnerReceiptEmail`, platform mail from `OWNER_EMAIL_FROM_ADDRESS` to the owner) re-reads the invoice and gives the amount paid in the invoice's currency, the payment date and the plan in the site's default language, with a "View your invoice" link to the invoice PDF (the hosted invoice page when Stripe has no PDF). An invoice that charged nothing sends no receipt. With no sender address or owner it is skipped and logged (`billing.receipt_unconfigured`, `billing.receipt_owner_missing`); a failed send is logged (`billing.receipt_failed`) and never makes Stripe retry.
- No worker step yet: a move to Growth starts the template-layer run once #5714 adds the enqueue to `onTenantPlanChange`; until then a Stripe upgrade, like an operator's, adds no template sections. Stripe secrets never go to the worker.
- **Price catalogue** ([pricing-module](./pricing-module.md)): `price.created`, `price.updated`, `promotion_code.created`, `promotion_code.updated` and `coupon.deleted` are handled before the subscription path (`handleCatalogueEvent`). Each re-reads the Price (with `currency_options`) or promotion code (with `promotion.coupon.applies_to` and `promotion.coupon.currency_options`, so an amount-off code keeps every currency's amount) from Stripe and saves it to `stripe_prices` / `stripe_promotion_codes`, or removes it when it no longer belongs: a Price that is archived or has no plan lookup key, a code that is inactive, restricted to a customer, to first-time buyers or to a minimum amount, past its `max_redemptions`, whose coupon is no longer valid, or whose coupon is amount-off in none of the billing currencies. `price.deleted` removes the Price's rows without a read; `coupon.deleted` re-reads that coupon's codes. Only `USD`, `EUR` and `GBP` amounts are kept. These events are not recorded with `recordStripeEvent`: each save is a re-read, so a replay writes the same rows. After each handled catalogue event, `revalidatePlatformSite` runs in `after()`: it finds the platform tenant by `TENANT_ROOT_DOMAIN` (`getTenantByDomain`) and calls web's `POST /api/revalidate-site-config` for it, the call a settings save makes, so the marketing pricing page shows the change on its next load. With no root domain it logs `billing.catalogue_revalidate_skipped`, with no tenant on it `billing.catalogue_platform_tenant_missing`, and a failed lookup `billing.catalogue_revalidate_failed`; none fails the webhook.

## Configuration

- `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (platform, `src/utils/stripe-env/stripe-env.ts`; required in production). `STRIPE_PUBLISHABLE_KEY` (same file, required in production) is the matching publishable key, passed from the server to the Upgrade page's Stripe.js; unset, Upgrade says it is unavailable and logs `billing.checkout_unconfigured`, as does a missing secret key or `PLATFORM_APP_BASE_URL` (Checkout's return URL). The SDK (`stripe` 23.1.0) calls the API at version `2026-10-28.endive`, and the webhook endpoint must be created at that version too: the handler reads an invoice's subscription from `invoice.parent.subscription_details`, which older versions do not send, so an older endpoint would silently write nothing and send no receipts on invoice events. The Stripe dashboard's webhook endpoint points at `https://<platform host>/api/stripe/webhook` and sends the five events above; Stripe's customer emails (receipts, failed-payment notices) are turned off there. Setting both is console work, human-gated.
- `OWNER_EMAIL_FROM_ADDRESS` and `RESEND_PLATFORM_API_KEY` for the receipt.
- The Stripe webhook endpoint must be subscribed to the catalogue events above as well as the subscription and invoice ones (Stripe dashboard, both modes). Once per mode, an operator copies what Stripe already holds: `pnpm --filter platform sync-stripe-catalogue --mode test` (or `--mode live`), run with the platform's full env loaded: it imports the platform env check, so besides `STRIPE_SECRET_KEY` and `DATABASE_URL` it refuses to start without `AUTH_SECRET` unless `SKIP_ENV_VALIDATION=1` is set, and the closing marketing-site refresh needs `TENANT_ROOT_DOMAIN` (else `billing.catalogue_revalidate_skipped`) plus `WEB_APP_URL` and `SITE_CONFIG_REVALIDATE_SECRET` (else `site_config.revalidate_skipped`). It refuses to run without `--mode test` or `--mode live` (`billing.catalogue_sync_mode_invalid`) and when the key is not an `sk_<mode>_` key (`billing.catalogue_sync_mode_mismatch`). The check compares the key with `--mode` only, never with the database: the operator points `DATABASE_URL` at the same environment as the key. It lists every Price by plan lookup key (ten keys per call, Stripe's limit) and every active promotion code, saves or removes each as the webhook would, then removes every stored Price and promotion code it did not list (`removeStripePricesExcept`, `removeStripePromotionCodesExcept`) — a listing that fails part-way removes nothing — logs `billing.catalogue_synced` with the counts, and refreshes the marketing site as the webhook does.
- A failed Stripe or Resend call is logged through `toLoggableError` (`apps/platform/src/utils/loggable-error/loggable-error.ts`): the error's name, its `errorCode` (Stripe's or Resend's code, else a cause's code), and, when present, Stripe's `errorType` (its error class), `statusCode` and `requestId`, which finds the call in the Stripe dashboard's request log. Never its message, `raw` or `param`, which can carry personal data.
- Stripe Tax needs its registrations set in the Stripe dashboard, and the Starter and Growth Prices must exist with the lookup keys in `STRIPE_PRICE_LOOKUP_KEY` and carry no trial period, so a trial owner pays at checkout — console work, human-gated.
- Cost: one Stripe API read per handled event (two for `invoice.paid`), free; one Resend email per paid invoice; per Upgrade mount a customer read or create, a subscription and an open-session list (plus an expire per open session), one Price lookup, one promotion-code lookup when `?promo=` is set, and one Checkout Session (two when Stripe refuses the code), all free. Each payment carries Stripe's fees (card processing, Billing ~0.7%, Tax ~0.5%).
